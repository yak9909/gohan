## 結論

**Claude案の「項目別登録」「定型パッチの表記述」「ホットキー有無による駆動規則」は採用を勧める。ただしItemSpecをそのまま最終形にはしない。** 値の読み書き・共有操作・結果と実行場所の契約を足した小さな構成が、本仕様には適している。

| 選択肢 | メリット | デメリット / 判断 |
|---|---|---|
| Claude案をそのまま実装 | パッチ・押下中・単発を項目別に登録できる。入口の変更が小さく分かりやすい | 連動値・通常アクション・非同期・失敗・終了処理は別設計が残る。将来それぞれに例外を足しやすい。チェック項目だけの第一歩なら有効 |
| **推奨：Claude案＋状態/値binding/機能処理の分離** | メニュー・ホットキー・チャットから同じ処理を呼べる。編集途中の値、適用失敗、非同期の扱いを共通化できる | 初回の登録APIと移行検証は増える。型・結果・実行場所を決める必要がある。追加機能が既に仕様にある本件では費用に見合う |
| 全チートのクラス階層、汎用イベントバス、外部定義言語 | 動的なプラグイン交換や高度な拡張には強い | 現仕様には過大。依存関係・メモリ所有・デバッグ経路が増える。現在は採らない |

これは設計上の判断。実機で性能や安全性を確認したという意味ではない。

## Claude案の不足とソース上の根拠

1. **項目別登録の対象がチェック系に寄っている。** §7.2には連動型のRead/Write、通常アクションの登録がない。現行 `Sources/GuiMenu.cpp:1790` 以降の `RunAction` はaction番号の分岐。`gohan.md` §14はアイテム投入・天気をメニューとチャットで共有すると明示している。
2. **「登録層だけ」の変更では確定仕様を満たせない。** `ApplyItem`（1745）は適用値を先に書き、`ToggleEvaluate`（1916付近）はvoidのSetActive後に無条件で通知する。数値確定（2256）とリスト確定（1566）は直接appliedへ代入する。共通Applyだけ改修しても、この経路には書込み処理・失敗処理が届かない。
3. **ライフサイクルが減っている。** 現行のOnEnable/OnDisableは `Includes/GuiMenu.hpp:146` 以降にあるが、提案ItemSpecはOnTickだけ。フック、入力監視、専用UIを持つ機能には開始・停止・解放の入口が必要。
4. **void/boolだけでは実行状態を表せない。** `ChatKanji.hpp` のRequest/Poll/Dismiss/Shutdownは既に非同期。Request受付は変換完了ではない。`PatchListIsActive`（2621）は「全てONでない」をfalseにまとめ、OFF・不一致・混在を区別しない。PatchListSetActiveは不正要素を飛ばして書き続ける。
5. **呼ぶスレッドは項目型からは決まらない。** `GuiMenu.cpp:2474` は専用スレッド。`ShizueSkip.cpp` はゲームのフレームフック内、ChatKanjiは専用workerとメニュー側Poll。任意のゲーム関数をメニューのOnFireへ直接移してよいとはいえない。
6. **indexと表示名への依存がある。** `ShizueSkip.cpp:48` 以降で日本語ラベルを検索。並べ替え・名称変更と機能の識別が結び付いている。登録順と恒久IDを分ける方がよい。

「3型を混在できない」は厳密には強すぎる。現在も全体ハンドラ内で項目ごとにdispatchすれば実現し得る。ただし中央の分岐が肥大化するため、項目別登録にする結論は妥当。

## 推奨する構成

```text
メニュー / ホットキー / チャット
        ↓ 型のある要求
項目制御（編集・適用・発火条件・確認・結果の表示）
        ↓ 共通の機能API
パッチ / 値の読み書き / アイテム投入 / 天気 / 漢字変換等
        ↓ その処理で検証した実行場所
ゲーム側フック / プラグイン内処理 / 専用worker
```

### 1. 定義・項目状態・機能の状態を分ける

- **ItemDef（変更しない定義）**：恒久ItemId、表示名、説明、所属・表示順、表示方法、振る舞い、binding/操作への参照。
- **ItemState（メニューが所有）**：編集値、適用値、編集中/適用済みホットキー、利用可否、処理中・結果表示。機能は原則として適用済みの設定のみ読む。
- **機能側の状態**：効果のON/OFF、フックの所有、実行中request、読み取り対象の世代。メニューのON/OFFと分離。効果の観測結果をUIのappliedの代用にしない。

ItemIdは表示ラベルや配列位置と独立した明示enum等にする。内部では固定配列のindexへ解決してよい。UI表示順の変更が保存設定やしずえの識別を壊さない。将来設定保存を実装するならschema版とIDで移行するが、今回は永続化機能そのものを追加する提案ではない。

### 2. 表示方法と振る舞いを分け、許可した組合せだけ作れるようにする

表示はCheckbox / Action / Number / Choice / Folder等。振る舞いはClaude案を整理した既定パターンを使う：

| 登録パターン | 契約 |
|---|---|
| Patch / StatefulEffect | §4.3のアーム・ホットキー反転・OFFで解除。Patchは同じ契約の定型実装 |
| HeldAction | 項目ONかつ修飾キー押下中に更新。開始/停止を含む。入力マスクだけでなくアナログ値を受け取れる |
| ArmedAction | 項目ONの間、ホットキーの立ち上がりで1回 |
| ImmediateAction | 項目ON/OFFを持たず、選択/ホットキーで1回。必要なら入力UIを開始 |
| ApplyOnce | 項目ONを適用すると1回。成功時のOFF復帰・結果表示は項目制御が担当 |
| ValueSetting | Read/Validate/Writeのbindingを持つ。数値、リスト、画像付き選択に共用 |

**単一のIB_CUSTOMへ全て逃がさない。** 独自パッチはStatefulEffect、複数段のUIはImmediateActionの実装、値の特殊な書込みはbindingで表す。共通の確認・入力抑止・結果処理は通る。

登録は種類別factory/overloadにして、無関係なnullptrや数値を並べる初期化を避ける。Patch数は配列から求め、重複ID・不正な組合せ・未登録callbackを登録時に拒否。型付きcallbackとconst定義の参照で実装できる。現在のMakefileはGNU++11、例外/RTTI無効。新しいC++標準・継承ツリー・std::function・毎フレームの動的確保は前提にしない。

全項目へ全callbackや結果bufferを持たせる必要はない。種別付きの小さなデータと共有const表で足りる。バイト数や速度の改善は未計測なので断定しない。

### 3. 値bindingと共有操作を用意する

bindingはRead、Validate、Writeを持ち、いずれも結果を返す。

- 移動量：プラグイン設定へ代入。座標移動は適用済み設定snapshotを読む。
- 所持金：メニューを開く時に1回読む。適用時には対象を取り直して検証し、書く。
- 天気：メニューとchatの双方が同じSetWeatherを呼ぶ。chatからUIのindexを探して押させる形にしない。
- 見た目：`スタイルを変更`から専用メニューを開き、設定と実行をまとめる（2026-09-14確定）。個別の値は専用メニューの編集状態とし、実行時に共通スタイル変更処理へ渡す。再構築まで機能側が引き受ける。
- アイテム投入：メニューとchatは入力の得方だけを変え、同じInsertItem処理へ渡す。

**値の型と表示形式も分離する。** hex/decimalは表示、整数/浮動小数/選択肢IDは意味。現行は全てs32でfloatも1/10単位。表示の都合で将来の精度を固定しない。固定小数のままならscaleと丸めを明示し、floatを許可する項目なら範囲・有限値・正規化を定義する。これを今すぐ汎用数値ライブラリへ作り替える必要はない。

連動値はメニューopen時の対象情報も持つ。ゲームが止まらないため、apply時に同じ対象か確認し、古いポインタへ書かない。この確認は「開いている間に毎フレーム値を同期する」とは別。

### 4. 「要求した」と「成功した」を分ける

操作結果は少なくともSuccess / Failure / Pendingを区別し、理由を返す。Pendingにはrequest番号を付け、完了後に成功/失敗を通知する。完了不明・取消不能も成功として扱わない。

- 値のWriteが成功した時点でappliedを更新。失敗時は適用済みに見せない。
- 非同期の受付だけでOK表示をしない。重複実行を抑止する。
- 通常の即時アクションに「適用待ち」は持たせない。処理待ちは別の状態。
- ApplyOnceのメニュー経路は束縛の有無を問わずON→適用で即実行し、成功時にOFFへ戻す。ホットキー経路は適用済みの束縛を使い、ON/アームを条件にせず、確認ダイアログの承諾後に同じ機能を呼ぶ。項目の編集値/適用値は変更しない（§7.4）。束縛設定だけの適用で実行しない。
- Dismissは表示を閉じる操作。既に走り始めた漢字変換を中断・解放したことにしない。現在のjoin/結果公開の契約を保つ。

UIの値・hotkeyだけ変更した時にOnFireを誤って呼ばない。X/一括適用/入力UI確定を同じ制御入口へ集約する。ただし、入力確定が編集だけか即適用かは仕様の意図に従い分岐し、全入力を強制的に即適用へ変えない。

一括適用は無条件の全体rollbackを約束しない。値設定、パッチ、アイテム追加等では可逆性が異なる。関連設定を先に検証・公開してから依存する動作を開始し、項目ごとの成功/失敗を返す。不可逆操作は明示的な確定時に1回だけ実行。依存関係がない部分の汎用グラフは不要。

### 5. 実行場所と終了処理を明示する

GuiMenuは描画とUI状態を所有し、機能はその処理で確認した場所で実行する。ゲーム主スレッドの必要性は機能ごとに検証し、全OnTick/OnFireがメニュースレッドで安全とは仮定しない。既存のしずえフックと漢字workerはadapterから利用する。

別スレッドへ渡すのはコピー済みの要求・設定snapshotと結果。容量の決まったqueue等を使い、満杯時はBusyを返す。callbackへ可変Itemの生参照を渡さず、共有状態の所有者と同期を決める。現在の機能単位のatomic/join契約を根拠なく置換しない。

登録/開始/停止/解放を区別する。メニュー画面を閉じても持続効果は続く。プラグイン終了・機能の解除では、その機能が所有するhookやworkerを終了させる。停止できる条件と待ち方を機能ごとに定義する。現行ShizueSkipの実行地点を新しい汎用callbackへ移さない。

項目の有効化/無効化に伴う準備・解放と、HeldActionのキー押下開始/終了も別にする。OnEnableをキー押下ごとに呼んでフックを再設置する設計にはしない。入力UIを開くActionはUI側の手順を開始し、入力完了後にUI非依存の機能APIへ渡す。

### 6. パッチは表を維持し、状態判定・検証を補う

TogglePatchの「明示on値/off値」は維持。初回の値を勝手にOFF値として保存する方式へ変えない。PatchSetに対応版・期待命令・根拠を結び付ける。

- 全ON / 全OFF / Mixed・Conflict / Unavailableを区別する。Mixedを単なるOFFとして反転しない。
- 適用前に全要素の整列・サイズ・範囲・元値・重複を確認し、不正な1要素だけ飛ばして成功扱いにしない。
- 他機能と同じ範囲を触る場合は拒否または明示した共有管理。解除で他の機能のpatchを消さない。
- 書込みとcache処理後に読み戻して結果を返す。OFF要求で解除できなければ成功表示にしない。
- 複数アドレスへのstoreはそれだけで原子的にはならない。ゲームが途中状態を読まない適用地点/同期を別途検証する。ロールバックも当該PatchSetについて検証できた範囲だけ。

元表とcache処理の知見は再利用できるが、現在のvoidのPatchListSetActiveを無条件で残して安全とする案にはしない。

## 根拠の範囲

今回の比較は仕様とC++ソースの独立照合。ゲームバイナリの新規解析・IDA・実機操作・ビルドはしていない。両仕様を上書きせず、この提案だけを保存した。旧資料のアドレスを新しい実装へ採用したわけではない。

型の明確なinterfaceと共有状態の同期という一般原則は [C++ Core Guidelines I.4](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Ri-typed)、[CP.2](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rconc-races)も参照。個別の設計選択は本仕様/現行コードからの提案で、ガイドラインを一律導入するものではない。
