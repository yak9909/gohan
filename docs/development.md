# 開発の進め方

G1 前半として、CTRPF の起動と状態表示、ゲームの毎フレーム処理への接続を備えています。
G1 後半でメニューの生成、G2 で機能、G3 で SD 資源の生成を整え、
G4 で利用者向けの説明を実装と照合します。

## 層と置き場所

依存の順序は `features → ui/world/menu → game → core` です。
途中の層を飛ばして下位を使えますが、上位への参照はできません。
ui・world・menu は互いを参照せず、別の機能の内部にも依存しません。
同じ機能の中ではヘッダーを共有できます。

| 場所 | 受け持つ物 |
| --- | --- |
| `src/core/` | ゲームに依存しない起動・終了、登録、フレーム処理、通信、文字・ファイルの処理 |
| `src/game/` | ゲームの型、番地、フックを隠す API と生成ヘッダー |
| `src/ui/` | 2D 描画、入力、キーボード、通知などの部品 |
| `src/world/` | 3D のカーソル、描画、資源の寿命の管理 |
| `src/menu/` | メニューの状態・描画・設定保存・ホットキー。機能との接続には ID を使う |
| `src/features/` | 利用者が使う各機能。機能間の共通処理は下位層へ移す |
| `spec/` | 人が編集するメニューや資源、設計値の定義 |
| `plugin/` | リンクとプラグイン情報の設定 |
| `tools/` | 生成・検査の道具。生成器は後で Python パッケージにまとめる |
| `third_party/` | 採用したソース・書体と元の通知 |
| `tests/tools/`・`tests/host/` | 自作の入力による Python と PC 向け C++ の試験 |
| `docs/` | 開発手順、機能と SD 資源の説明。メニュー一覧は定義から生成する |
| `build/`・`out/` | 中間生成物と配布用出力。収録しない |

ソースとヘッダーは同じ役割のフォルダに置きます。1 ファイルの責務を絞り、
600 行程度を超えたら分割を検討します。C++20、UTF-8、clang-format を使い、
例外・RTTI や大きな標準ライブラリへの依存を避けます。
書式処理は core にまとめ、容量の上限も一か所で管理します。
CTRPF の機能を保ちつつ、実測とリンクマップでサイズを確認します。

ゲームの状態はゲームの描画スレッドで操作します。メニューは入力・設定を担当し、
作業スレッドは計算を担当します。受け渡しには core の Mailbox・Request を使い、
各機能で atomic や volatile による通信を実装しません。

## 入力と生成物の扱い

| 区分 | 入力と出力 | 収録方針 |
| --- | --- | --- |
| 番地・型 | 名前による API 定義と symbols から `src/game/generated/api.hpp` を作る | ヘッダーを収録。照合用の値は命令そのものではなくハッシュにする |
| 設計値 | 座標・色・表・カメラ曲線を `spec/tables/` などで編集する | gohan の設計として収録し、変更はその定義に加える |
| ゲームの資源 | 手元の ROM 展開物から画像・レイアウトを `out/sdmc/` へ生成する | 入出力は収録せず、生成器と手順を収録する |
| 自作の生成物 | メニュー・字形・キーボード・スタブを定義や書体から `build/` へ生成する | 入力を収録し、ビルド時に出力を作る |

3gx のビルドには ROM を要求せず、SD 資源の生成だけが ROM 展開物を読みます。
生成時は入力の版と出力のハッシュを manifest に残します。
ゲームの型・名前が不足する場合は先に定義を整え、機能側で番地やオフセットを補いません。
フックに必要な元の命令は実行中のメモリから取得します。
形式の読み書きは自前で実装する方針で、3DSkit は依存に加えません。
第三者の物を導入するときは通知と変更点も一緒に追加します。

## プラグインのビルド

Python 3.11 以上、devkitPro の devkitARM・libctru、MSYS2 の make と基本コマンド、
3gxtool を用意します。ROM とネットワーク接続は不要です。
`src/game/generated/api.hpp` は収録済みの物を使い、通常の make では再生成しません。

PowerShell では devkitPro の MSYS2 を PATH の先頭に置き、プロジェクト直下で実行します。

```powershell
$env:DEVKITPRO = 'C:/devkitPro'
$env:DEVKITARM = 'C:/devkitPro/devkitARM'
$env:PATH = 'C:\devkitPro\msys2\usr\bin;C:\devkitPro\devkitARM\bin;' + $env:PATH
make -j4
make -j4 DEV=1
```

devkitPro のシェルで設定済みなら `make` だけで作れます。
先に同梱 CTRPF をソースからビルドし、`src/` 以下のソースを再帰的にコンパイルします。
出力は `out/gohan.elf` と `out/gohan.3gx`、リンクマップは `build/gohan.map` です。
`make DEV=1` は `GOHAN_DEV` を定義し、状態表示にも開発版と出します。
`make LTO=1` は LTO を試す設定です。既定では無効で、実機の動作確認は別途必要です。
設定ごとのオブジェクトは `build/plugin-dev<DEV>-lto<LTO>/` に分けます。
`make BUILD=build/<名前>` でプラグインの中間生成先を分けることもできます。
CTRPF 書庫は共通の `build/libctrpf/`、配布物は共通の `out/` を使います。
`make clean` は既定の `build/` と `out/` を削除します。

毎回リンクし直し、3GX の変換成功後に `.text`・`.rodata`・`.data`・`.bss` の容量と
前回からの差を表示します。前回値は `build/size_last.json` に保存し、初回は「初回」と表示します。
BUILD を変えた場合はその中に map と前回値を置きます。
これは指定した四つの ELF セクションの測定で、TLS・配列初期化などの付随セクションや
3GX のファイル容量とは一致しません。

対応するゲームで CTRPF のメニューを開くと「gohan（作り直し中）」が現れます。
押すと 3.0.0、通常版／開発版、骨格と毎フレーム接続の状態を表示します。
実機での起動・表示・終了と、更新が異なる場合の拒否は実機確認の対象です。

## CTRPF 単体のビルド

同梱の CTRPF 0.8.0 と libcwav・libncsnd をソースからビルドできます。
ROM やネットワーク接続は必要ありません。
ソースの版・変更点は [PATCHES.md](../third_party/libctrpf/PATCHES.md)、
ライセンスは [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) を参照してください。

devkitPro の devkitARM、libctru、MSYS2 の make と基本コマンドを用意します。
Windows の PowerShell では、プロジェクト直下で次を実行します。

```powershell
$env:DEVKITPRO = 'C:/devkitPro'
$env:DEVKITARM = 'C:/devkitPro/devkitARM'
$env:PATH = 'C:\devkitPro\msys2\usr\bin;C:\devkitPro\devkitARM\bin;' + $env:PATH
& C:\devkitPro\msys2\usr\bin\make.exe -C third_party/libctrpf -j4 release
```

devkitPro のシェルで環境変数が設定済みなら、`make -C third_party/libctrpf -j4` でも同じです。
`release`（既定）は `build/libctrpf/libctrpf.a`、`debug` は `build/libctrpf/libctrpfd.a` を作ります。
どちらにも libcwav・libncsnd を結合するため、利用側はこの書庫と libctru 等をリンクします。
ヘッダーは `third_party/libctrpf/include/` を参照します。devkitPro 内へのインストールは不要です。

中間生成物は `build/libctrpf/release/`・`debug/`、音声ライブラリは
`build/libctrpf/libcwav/`・`libncsnd/` に置きます。
`make -C third_party/libctrpf clean` はこれらを含む `build/libctrpf/` だけを削除します。
ソース側への生成や、依存ソースの自動取得・更新は行いません。
`install` は開発環境のライブラリを上書きしないよう無効にしています。

## 検査

メニューの見た目は、実際のコードを PC で動かす [プレビューと実機画像の比較](preview.md) で
確認できます。時刻付きの入力台本から、上下画面の PNG と1ファイルの HTML を作ります。

```sh
python tools/check.py --all
python -m pytest tests/tools
python tests/host/run.py --cxx g++
python tools/check.py --staged
```

Python 3.11 以上を使います。check.py に追加パッケージは不要で、試験だけ pytest を使います。
CI の必須チェック名は `audit` です。
PC 試験は g++ または clang++ の C++20 対応版を使います。自動検出、`--cxx`、
環境変数 `HOST_CXX` で指定でき、出力は `build/host/` に限ります。
Windows で MSYS2 の g++ を使う場合は、そのコンパイラの bin を PATH の先頭に置き、
依存 DLL も同じ環境から解決してください。CI は Ubuntu の g++ を指定します。
試験は書式の境界、UTF の不正入力・容量不足・全スカラー値の往復、
Mailbox・Request の別スレッド間の連続受け渡し、フレーム登録と終了順序を確かめます。
ゲーム側の接続も、自作の入力と CTRPF の代役で、タイトル・読み取り・CRC の失敗時に
導入しないことと、成功・終了時の呼び出しを確認します。実機の代わりにはなりません。
`--all` は追跡中のファイルを、`--staged` は削除を除いたコミット予定の内容を検査します。
後者は作業ツリーではなくインデックスから読み、許可リストも同じ状態を使います。

ワーカーは git・gh を実行できないため、呼び出し元が渡した相対パス一覧を使います。

```sh
python tools/check.py --all --files-from file-list.txt
python tools/check.py --all README.md tools/check.py
```

一覧は UTF-8 の改行または NUL 区切りです。明示的な一覧や位置引数があれば、
どちらのモードでも git を呼ばず、手元のファイルを読みます。
この方式の `--staged` はインデックスとの一致を保証しないため、最終確認は取り込み側で行います。
空の一覧も扱えます。一覧の完全性は呼び出し元の責任です。

検査はゲームの形式、生成先・ローカル設定、1 MB（1,000,000 bytes）超、個人用の絶対パスを拒否します。
C/C++ の `src/` 配下では include の依存方向、game 以外の番地らしい数値、
core 以外の `std::atomic`・`__atomic`・`volatile` を調べます。
番地判定の範囲は 16 進数の `0x00100000` から `0x3FFFFFFF` までです。
include は `src/層/`、`層/`、相対パスに対応します。
コメントと文字列はコードの数値・通信検査から除外します。
マクロで組み立てた include や式の評価を行う C++ コンパイラではないため、
レビューでも層とゲーム API の境界を確認してください。

例外が必要な自作の試験用ファイルなどは `tools/check_allow.toml` に、
正確な相対パス・規則名・理由を指定します。内容の検査は行番号でも絞れます。
フォルダ全体の免除は設けません。検査は成功で 0、違反で 1、読み込みや設定の失敗で 2 を返します。

解析に関する参照の持ち込みは作業場の別の検査が担当します。
メニュー定義と生成出力の一致は、生成器を追加する G1 で検査に接続します。
その入力・出力は G1 後半で追加します。

## 起動・フレーム・通信の契約

`main.cpp` は構成の接続点です。CTRPF のメニューを作り、ゲーム側が公開する
Feature を core の登録表に渡して Wire・Shutdown を呼びます。
登録表はゲームを読み込まず、ID の重複・容量超過・起動後の追加を拒否します。
Wire に失敗した機能は自分で原状に戻します。終了はゲームのフック、描画のフック、
それ以外の順に、同じ段では登録と逆の順で一度ずつ呼びます。
Wire・Shutdown から同じ登録表を呼び直すことはできません。

ゲームの接続はタイトル ID と生成された CRC-32 を、ゲームを停止して照合します。
不一致・読み取り失敗ではフックを入れません。元の命令は実行時に CTRPF が保存・復元します。
ゲームのフック位置・型・メモリ操作・アセンブリは `src/game/` に限り、
ゲーム側のコールバックは `core::frame::Dispatch()` を一つ呼びます。

フレームの登録は小さい order が先、同値は登録した順、同じ関数は一枠だけです。
Add・Remove の結果は Queued・Unchanged・Full・Busy・Invalid を返します。
Queued は次のフレーム境界で反映し、Busy は呼び出し側で後の機会に再試行します。
実行中に登録・解除しても現在のフレームの一覧は変わりません。
Remove の返した世代について IsApplied が真になってから、その処理の資源を解放します。
未確認の変更を約21億回以上ためないでください。Reset はフックを外し、ゲーム側から
呼ばれない状態でのみ行います。

Mailbox は固定長の二重バッファと世代で最新の状態を渡します。読み飛ばしを許す状態用です。
TryPublish の false、ReadIfNew の Busy はコピーの競合を意味し、後で再試行します。
読み取り先の世代は読み手ごとに保持します。約43億回の更新をまたぐ読み取り停止は避けます。
Request は一枠の要求です。受理した値を一度だけ取り出し、満杯なら次の要求を拒否します。
どちらも値は trivially copyable な固定長型とし、ポインタ先の寿命は自動管理しません。
容量は `src/core/limits.hpp` で管理します。

TextWriter の容量は終端を含み、切り詰めは Complete で検出します。
UTF 変換は文字途中の切り詰めを避け、不正入力を置換文字にして valid を false にします。

## 自前の描画

画面の内容は `ui::renderer` の `Canvas` に矩形・文字・画像として描き、画面ごとに `Commit` します
（上画面と下画面は別々に置き換わるので、使う側が互いの画面に触れません）。
使う側は `SetEnabled(Client, bool)` で描画の導入を求め、全員が取り下げると取り外します。

導入と描画は `game/lyt` が受け持ちます。ゲームの描画スレッド（毎フレームの処理）だけが触ります。

CA2 の設計値は `spec/ui.toml` に置き、make が `build/gen/ui_values.hpp` を作ります。
自作の型紙から `ui_parts.hpp`（位置・寸法・分割）と `ui_atlas.hpp`（RGBA8）も生成します。
色と不透明度は設計表の 8 ビット値をそのまま保ちます。UI は 32,768 バイト、
横・縦の破線は各 256 バイトで、字形を含む確保は 98,816 バイトです。
`core/limits.hpp` の画像予算と生成物の容量をコンパイル時に照合し、
導入後に残すヒープの空き 400,000 バイトは減らしません。
閉じた後の常駐は管理・整列の余裕を含めて 99,072 バイト、上限は 120,000 バイトです。
窓と帯の追加画像 196,608 バイトは、メニューが背景を描く時だけ借り、閉じた後の
ノード・GPUの参照を8フレーム排出して返します。予備を残せない時は単色の帯で開きます。
合成元のプレビュー専用画像はプラグイン側に残し、ゲームのヒープへ複製しません。
`Image` はアトラスの部分を整数倍・頂点色付きで描き、`PartBox` は部品ごとの
9 分割・横 3 分割・縦 3 分割を使います。分割を直接指定する API もあります。
`Repeat` は独立した破線の画像を 1 枚の板で繰り返し、位相と整数倍を指定できます。
アトラスの各部分を繰り返す API にはしていません。分割の途中で予算が足りなくなると
その部品を丸ごと取り消します。板は上 144・下 48、文字は各画面 48 のままです。

- 導入は、タイトルと各入口の照合に通り、さらにゲームの管理者・文字の処理器・ヒープの空きが
  そろった時だけ行います。そろわなければゲームの資源を何も確保しません。
- Pane・Picture・TextBox・Material・ResFont はプラグインのメモリに置き、GPU が読む字形・UI のアトラスと
  記録用のコマンドリスト（上下 1 本ずつ）だけをゲーム側から借ります。
  画像はレイアウト用ヒープ、記録列等295,944バイトは別の描画命令用ヒープから取ります。
- 画面ごとの Layout ノードは、毎フレーム、ゲームの管理者の上下のリストに登録します
  （ゲームは描画のあとにリストの全ノードを外します）。描くものが無い画面は登録しません。
- 木はノードがリストに載っていない間にだけ組み替えます。
- 取り外しは、ノードがリストから外れ、数フレーム待って GPU が使い終えてから、リストとアトラスを返します。
  終了時は、毎フレームのフックを止める前にこの排出を済ませるため、描画の部品の終了の段を
  「ゲームのフック」とし、フックの機能より後に登録します（同じ段は登録と逆の順に止まります）。
- 切り抜きの範囲にかかる文字列は、範囲に完全に入る字だけを描きます（部分的にかかる字は描きません）。
