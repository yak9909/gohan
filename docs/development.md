# 開発の進め方

G0 は文書と検査の土台です。実装のディレクトリや生成器は、使う段階で追加します。
G1 で最小の起動とメニュー、G2 で機能、G3 で SD 資源の生成を整え、
G4 で利用者向けの説明を実装と照合します。

## 層と置き場所

依存の順序は `features → ui/world/menu → game → core` です。
途中の層を飛ばして下位を使えますが、上位への参照はできません。
ui・world・menu は互いを参照せず、別の機能の内部にも依存しません。
同じ機能の中ではヘッダーを共有できます。

| 場所 | 受け持つ物 |
| --- | --- |
| `src/core/` | ゲームに依存しない起動・終了、登録、フレーム処理、通信、文字・ファイルの処理 |
| `src/game/` | ゲームの型、番地、フックを隠す API と生成ヘッダー |
| `src/ui/` | 2D 描画、入力、キーボード、通知などの部品 |
| `src/world/` | 3D のカーソル、描画、資源の寿命の管理 |
| `src/menu/` | メニューの状態・描画・設定保存・ホットキー。機能との接続には ID を使う |
| `src/features/` | 利用者が使う各機能。機能間の共通処理は下位層へ移す |
| `spec/` | 人が編集するメニューや資源、設計値の定義 |
| `plugin/` | リンクとプラグイン情報の設定 |
| `tools/` | 生成・検査の道具。生成器は後で Python パッケージにまとめる |
| `third_party/` | 採用したソース・書体と元の通知 |
| `tests/tools/`・`tests/host/` | 自作の入力による Python と PC 向け C++ の試験 |
| `docs/` | 開発手順、機能と SD 資源の説明。メニュー一覧は定義から生成する |
| `build/`・`out/` | 中間生成物と配布用出力。収録しない |

ソースとヘッダーは同じ役割のフォルダに置きます。1 ファイルの責務を絞り、
600 行程度を超えたら分割を検討します。C++20、UTF-8、clang-format を使い、
例外・RTTI や大きな標準ライブラリへの依存を避けます。
書式処理は core にまとめ、容量の上限も一か所で管理します。
CTRPF の機能を保ちつつ、実測とリンクマップでサイズを確認します。

ゲームの状態はゲームの描画スレッドで操作します。メニューは入力・設定を担当し、
作業スレッドは計算を担当します。受け渡しには core の Mailbox・Request を使い、
各機能で atomic や volatile による通信を実装しません。

## 入力と生成物の扱い

| 区分 | 入力と出力 | 収録方針 |
| --- | --- | --- |
| 番地・型 | 名前による API 定義と symbols から `src/game/generated/api.hpp` を作る | ヘッダーを収録。照合用の値は命令そのものではなくハッシュにする |
| 設計値 | 座標・色・表・カメラ曲線を `spec/tables/` などで編集する | gohan の設計として収録し、変更はその定義に加える |
| ゲームの資源 | 手元の ROM 展開物から画像・レイアウトを `out/sdmc/` へ生成する | 入出力は収録せず、生成器と手順を収録する |
| 自作の生成物 | メニュー・字形・キーボード・スタブを定義や書体から `build/` へ生成する | 入力を収録し、ビルド時に出力を作る |

3gx のビルドには ROM を要求せず、SD 資源の生成だけが ROM 展開物を読みます。
生成時は入力の版と出力のハッシュを manifest に残します。
ゲームの型・名前が不足する場合は先に定義を整え、機能側で番地やオフセットを補いません。
フックに必要な元の命令は実行中のメモリから取得します。
形式の読み書きは自前で実装する方針で、3DSkit は依存に加えません。
第三者の物を導入するときは通知と変更点も一緒に追加します。

## 検査

```sh
python tools/check.py --all
python -m pytest tests/tools
python tools/check.py --staged
```

Python 3.11 以上を使います。check.py に追加パッケージは不要で、試験だけ pytest を使います。
CI の必須チェック名は `audit` です。
`--all` は追跡中のファイルを、`--staged` は削除を除いたコミット予定の内容を検査します。
後者は作業ツリーではなくインデックスから読み、許可リストも同じ状態を使います。

ワーカーは git・gh を実行できないため、呼び出し元が渡した相対パス一覧を使います。

```sh
python tools/check.py --all --files-from file-list.txt
python tools/check.py --all README.md tools/check.py
```

一覧は UTF-8 の改行または NUL 区切りです。明示的な一覧や位置引数があれば、
どちらのモードでも git を呼ばず、手元のファイルを読みます。
この方式の `--staged` はインデックスとの一致を保証しないため、最終確認は取り込み側で行います。
空の一覧も扱えます。一覧の完全性は呼び出し元の責任です。

検査はゲームの形式、生成先・ローカル設定、1 MB（1,000,000 bytes）超、個人用の絶対パスを拒否します。
C/C++ の `src/` 配下では include の依存方向、game 以外の番地らしい数値、
core 以外の `std::atomic`・`__atomic`・`volatile` を調べます。
番地判定の範囲は 16 進数の `0x00100000` から `0x3FFFFFFF` までです。
include は `src/層/`、`層/`、相対パスに対応します。
コメントと文字列はコードの数値・通信検査から除外します。
マクロで組み立てた include や式の評価を行う C++ コンパイラではないため、
レビューでも層とゲーム API の境界を確認してください。

例外が必要な自作の試験用ファイルなどは `tools/check_allow.toml` に、
正確な相対パス・規則名・理由を指定します。内容の検査は行番号でも絞れます。
フォルダ全体の免除は設けません。検査は成功で 0、違反で 1、読み込みや設定の失敗で 2 を返します。

解析に関する参照の持ち込みは作業場の別の検査が担当します。
メニュー定義と生成出力の一致は、生成器を追加する G1 で検査に接続します。
G0 にはその入力・出力がまだありません。
