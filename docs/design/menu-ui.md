# メニューの見た目

**決定: CA2（2026-10-20）**。実装の正本は「決定: CA2」の節。ほかの案（GA1・GC1〜3・CA・A・B・C）は、決めるまでの資料として残す。

上画面（400×240）に出すメニューの見た目の案。選ばれた案の値（色・寸法・間隔・時間）を `spec/` の設計値にして実装する。メニューの振る舞い（3 状態の行・実行の項目の予約と OK・フォルダ・値の入力の枠・確認のダイアログ・通知・長押しの進み棒）は今のエンジンのままで、ここで決めるのは見た目と、上画面に移すことで変わる操作だけ。

利用者は案 C（3 列）を選び、全ての字をゲームの書体で描き、UI もゲームの実際の UI に合わせる前提にした。その後、ゲームの版の GC1 の見た目に、案 A の配置と選び方を組み合わせることにした（GA1）。次の版を並べる。

- **GA1（GA 節）**: 利用者が選んだ GC1（掲示板）の見た目で、配置と選び方を案 A（左に項目の一覧、右上に説明。説明の場所を選択の枠として使う）にした版。利用者の指摘 1〜15 を直した。
- **ゲームの書体とゲームの UI の版（G 節）**: 案 C を土台にした 3 つ。字と部品の前提（G.0）は GA1 にも当てはまる。
  - GC1「掲示板」: 親・今・説明の 3 列を、ゲームの一覧の板（金の縁・生成りの地・吊り紐とピン）で描く。
  - GC2「タブ」: 親の列のかわりに、1 段上のフォルダの項目をゲームのタブで題の下に並べ、一覧と説明の 2 列にして字の幅を広げる。
  - GC3「吹き出し」: 親と今の 2 列を上に、説明をゲームのメッセージの窓の形で画面の下に置く。
- **ドット絵の版（0〜5 節。前の案を残す）**: 字は美咲ゴシック第2と PixelMplus、部品は自作のドット絵。
  - 案 A「木の窓」: 一覧と説明の 2 列。
  - 案 B「すりガラス」: 左に半透明の 1 枚。
  - 案 C「3 列の帳面」: 親・今・説明の 3 列（指の向き・自作のボタンの印・上向きの印を直した）。

寸法と色は実寸の画素で書く。座標は上画面の左上が原点。色は `#RRGGBB`、不透明度は `/ 0.94` のように後ろに書く（`spec/` では `0xAARRGGBB` にする）。ゲームの画像を塗る色は「黒の色 → 白の色」（画像の濃さ 0 の所を黒の色、255 の所を白の色にする 2 色の補間）で書き、各色は (R, G, B, A)。

## 決定: CA2（2026-10-20）

利用者は、実装する見た目を **案 CA2「CA × タイトル画面の背景」** に決めた。**この節が実装の正本**で、`spec/` の設計値はこの節の表から作る。ほかの節（GA・G・0〜5）は、決めるまでの経過と、比べた案の資料として残す（値が食い違う時はこの節を正とする）。

- 見た目: 案 C の見た目（紙の窓・緑の帯・ドット絵の書体と印）で、案 A の配置（左に一覧の窓、右上に説明の窓、下に操作の帯）。値の入力・選択・割り当ての枠は説明の窓の場所に出す（説明の場所を選択の枠として使う）。
- 窓の地にタイトル画面の下画面の背景をクリーム色の濃淡に写して薄く重ね、選択中の帯の地は同じ背景を緑に写してゲームと同じに動かす。
- 字はドット絵の書体（美咲ゴシック第2・PixelMplus の数字）。読めない漢字は字形を描き直すか仮名にし、前後の言葉で読める漢字は残す（D.4）。
- 振る舞い（3 状態の行・予約と OK・フォルダ・入力の枠・確認・通知・長押し）は今のエンジンのまま。
- 直しの依頼が来ても、D.2〜D.8 の表の値を変えるだけで済むようにする。値の名前は `spec/` の設計値の名前（`ca2.` で始まる）にする。表に無い値を実装に直書きしない。

見本の絵は作業場の外（Git に入れない）にあり、CA2 の全場面（17）を同じ値で描いてある。

### D.1 書き方

- 座標は上画面の左上が原点の画素。`(x, y, 幅, 高さ)`。「窓 x」「行 x」などは、その部品の左上からの差。
- 色は `#RRGGBB`、不透明度は `/ 0.88` のように後ろに書く（`spec/` では `0xAARRGGBB`）。
- 型紙の「9 分割」は角を固定して辺と中を伸ばす、「横 3 分割」は両端を固定して中を横に伸ばす、「縦 3 分割」は上下を固定して中を縦に伸ばす（0.2・0.3 節の規則）。拡大は整数倍だけ、置く位置は整数の画素。

実行時に更新側、失敗したら本体側の RomFS を試す。開く段階だけでなく、対象が無い・読み出し・形式の検査で失敗した場合も本体側へ進む。片方の資源から 2 枚がそろった場合だけ採用し、取り違えを防ぐ。状態表示には各側の失敗段階と FS の Result（16 進）を残す。読めなかった時もメニューは代わりの色で動く。

`Assemble(frame)` は 150 で剰余を取り、位相を `frame / 150` として 6 枚の四隅の位置・UV・色・不透明度を返す。位置は画面中央からの差で、画面の y は下向き。UV は繰り返しの単位で v が下向き。4 枚の反転は板の幅と高さの符号で表す。`Sample` は繰り返しの線形サンプリングで格子・縞 4 枚・点の順に合成し、RGB の輝度（0.299R + 0.587G + 0.114B）を上の区間に写す。範囲外の輝度は端の色にする。

窓は `ca2.titlebg.window.image_size = (256, 256)` の 0 コマ目を CPU で合成する。最大の窓 228×210 を覆う最小の 2 の冪が 256×256。6 枚の合成後の輝度を指定区間で clamp した係数だけを L4（Morton 順、下位ニブルが先）へ丸める。GPU ではマテリアルの黒の色 `ca2.window.overlay.color[0]` → 白の色 `[1]` で補間し、不透明度 0.14（36/255）はペインに設定する。RGBA8 のクリーム色・不透明度の焼き込みは行わない。L4 の丸めによる係数の誤差は最大 1/30、色成分の誤差は黒白の差の 1/30 以下。各窓の内側の左上から同じ停止画像を使い、任意の大きさでの厳密な周期タイルにはしない。

描画資源用ヒープの常駐画像は字形A4 32,768・UI 32,768・横/縦の破線各256・窓L4 32,768・帯L4 2,048×10の計**119,296バイト**。一括確保の管理・整列の余裕1,024を含む上限は**120,320バイト**。`core::limits::RendererResidentHeapLimit` を静的検査・実行時検査・PC試験で守る。元画像2枚の2,048バイトはプラグイン側に置き、GPUへ複製しない。字形の送り・色・影を保ち、二値画素の不透明度だけを下位ニブルから詰める。

字形・UI・窓・帯は導入時にすべて借り、メニューの開閉で確保し直さない。総量と最大の塊は導入前後に検査する。開く時の空きによって背景を省く・単色に替える処理や、ゲームの入力を遮断する処理は設けない。

閉じるアニメーションの後も全画像と記録列を保つ。描画全体の取り外しでは、ノードが外れてから参照の排出を待ち、まとめて返す。

動く帯は **そのフレームの1コマをCPUで合成し、256×16 L4の10面を巡回する**。150位相・1フレームごとの更新と、182×11の内側を同じ小数位置・線形標本・6層のsource-over・輝度のclamp・L4丸めで描く式を保つ。上下で同じ面を選ぶ。帯のGPU用画像は20,480バイト。GPUで6層を再合成する方式へは変えない。

| 名前 | 値 |
|---|---|
| `ca2.titlebg.selection.image_size` | 合成時の作業画像 256×16、L4、2,048 バイト |
| `ca2.titlebg.selection.cell_size` | 1面のうち実際に描く182×11画素。150位相の値・速度・毎フレーム更新を保つ |
| `ca2.titlebg.selection.update_frames` | 1。ゲームの毎フレームに1コマ進める |

帯の面は、両画面の適用済みの記録から参照されなくなったPresentを8回数えてから再利用する。木の更新が延期された画面の旧参照も残し、最後に公開した面も保護する。1フレーム1面では9面で循環し、順序の余裕を加えて10面とする。面へ書いた後にCPUデータキャッシュを排出し、成功した面だけを公開する。帯のPictureは遅延中の板を先に流し、GPUレジスタのテクスチャキャッシュ無効化ビットを明示的に記録してから描く。保存列の再生時にも無効化命令が流れ、テクスチャ状態の差分判定に依存しない。

毎フレームの合成は輝度の線形性を使い、同じ6層のsource-overを1成分へまとめる。UVの基底をQ28、標本位置をQ22、輝度と不透明度をQ24で持つ。182×11の端までのUVの誤差と6層の補間・合成の切り捨てを合わせ、輝度の差を192/2²⁴未満に抑える。この差を15段階へ写した値は1/2048未満。L4の丸め境界から1/2048以内の画素だけ、従来と同じdoubleのRGB式と座標で計算し直す。境界から離れた画素は同じL4値に丸まる。実入力と6種類の自作入力を全150位相で照合する。GCCではこの合成だけO2を指定し、fast-mathは使わない。
誤差の内訳と照合範囲は[帯のCPU合成と丸め](selection-compositor.md)にまとめる。

GPUの無効化はテクスチャ設定の第3バイトだけを書く。[公開実装の同じマスクとビット](https://github.com/devkitPro/citro3d/blob/master/source/base.c)も照合した。ゲームの差分キャッシュを直接書き換えず、既存の板を流してから無効化命令を積む。

### D.10 実行時にゲームの RomFS から読む物

gohan.3gx は ROM 無しで作る。ゲームの資源と派生画像は 3gx・gohan の作業ツリー・SD に保存しない。プラグインの初期化スレッドでゲーム自身の RomFS を読み、必要な画像だけをメモリ内で復号する。描画フックは完成した画像を受け取り、ファイルを読まない。

**ゲームの資源からメモリ内で作る物（保存・同梱しない）**

| 物 | 元 | 作り方 |
|---|---|---|
| タイトル画面の背景の 2 枚（16×16） | `Layout/Title/opng_titl.arc` の `timg/my_opn_bg_00.bclim`・`my_opn_bg_01.bclim` | RomFS と DARC の表は小分けに読む。画像の 168 バイトだけを読んで A4・L4 を復号する。レイアウト・アニメーションは読まず、D.6 の設計値を使う |
| 窓の地の背景 | 同上 | D.6 の 0 コマ目の合成後の輝度を区間に写した固定画像。GPU 用の Morton 順・L4 で登録し、マテリアルの黒→白の色とペインの不透明度でクリーム色にする |
| 選択中の帯の緑の停止見本 | 同上 | 同じ合成後の輝度を緑の 2 色へ写す。動く帯は上記の10面のL4画像を使う |
| 手のカーソル | 使わない | CA2 の手は自作のドット絵（`ca2.cursor.image`）。ゲームの手の画像は使わない |

ゲームの書体・ゲームの UI の画像・下画面のメニューの背景（`my_mvm_check`）は CA2 では使わない。

RomFS は自分自身のアーカイブを、長さ 1 の空のアーカイブパスと 12 バイトのバイナリのファイルパスで開く。更新側は `{5, 0, 0}`、本体側は `{0, 0, 0}`。別タイトルの保存領域・コンテンツ用のアーカイブは使わない。RomFS は IVFC 付きと第 3 層の先頭からの両方を扱い、対象までのディレクトリとファイルの兄弟だけをたどる。表・ファイルの範囲と循環を検査し、アーカイブ全体や RomFS 全体をヒープに確保しない。成功・失敗とも開いたハンドルを閉じる。

CPU側の木・文字枠を含む描画エンジンはプラグイン自身のヒープへ置く。ゲームの描画資源用ヒープにCPU用領域を置かない。失敗時は公開せずに巻き戻し、取り外しではノード・GPUの排出後に解放する。Mailboxも読み書きとも同じロック内でコピーし、値を二重保持しない。静的区分の合計は両版とも2MiB未満を検査する。

予算は手紙の場面から逆算する。便箋のモデル131,456バイトと画像131,072バイトの後、gohanを引く前の概算の空き228,580バイトから、常駐上限120,320を引くと**108,260バイト**残る。画像本体119,296だけなら109,284バイト。これは同じ場面と割り当て順を仮定した算術であり、未観測の消費と断片化は実機で確認する。

記録列の確保元はコードの呼び出し経路で確認した。`GpuCmd_CreateLists` は管理欄68バイト、`GpuCmd_AllocateListStorage` は記録本体とGX列を、いずれもメモリ種別 `65536` の確保コールバックへ要求する。描画の初期化が登録するコールバックは描画メモリ管理者の確保関数へ渡し、その種別は管理者の描画命令用ヒープを選ぶ。このヒープは初期化時に独立して作られ、画像用のレイアウトアロケーターのヒープとは別である。2本の記録147,456×2、GX列28×16×2、管理欄68×2の計**295,944バイト**（ヒープ自身の管理費は別）はこの経路を使い、画像用ヒープの常駐量へ加算しない。常駐確保後の空きの実差分も測り、想定外に同じヒープが減って120,320を超えれば導入を巻き戻す。

開発版の状態表示は、画像用ヒープの確保直前・直後・現在の空き総量と最大の塊、字形・UI（破線込み）・窓・帯の各取り分、管理込み上限と予算を出す。プラグイン側CPUエンジン量、別ヒープの記録列量、帯合成の現在・平均・最大時間（µs）と標本数、面の更新不能回数も出す。現在値は30フレームごとに採取する。PC試験では開閉100回の無追加確保、低空き時の窓維持、上限の境界、片画面の旧参照、登録中の木の更新延期、300フレームの巡回とCPU排出失敗を確認する。

GPU可視メモリをプラグインが独自に確保するシステムコールは使わない。画像は既存のゲーム側アロケーター、CPU用の木・文字枠と合成元はプラグインのヒープまたは静的領域、記録列は既存の描画命令用コールバックを使う。

8回の非参照待ちは既存の安全規則であり、GPU遅延の上限を証明するフェンスではない。ゲームの実行中GXリストのqueued/submitted/completedは参照できるが、今回の面と親リストの提出世代・最後の参照要求を結ぶ実機の確認は済んでいない。pointerや完了数だけで安全と判定せず、この版では10面と既存の待ちを使う。異常なGPU遅延・HOME復帰と実機の合成時間は引き続き確認する。

プレビューは `gohan.local.toml` の任意の `[rom] acnl_update_romfs`・`acnl_base_romfs`（直下に `Layout/` がある展開済み RomFS のルート）を使う。相対パスは設定ファイルの場所を基準にする。未指定なら代わりの絵にする。設定例は `gohan.local.toml.example`。同じ C++ の DARC・BCLIM 復号・合成・色変換を使い、`python tools/preview.py --parts --out <作業ツリー外の出力先>` で背景の停止見本も確認できる。ROM を使う場合は作業ツリー内の入力・出力を拒否し、実行ファイルだけを通常の `build/` に置く。

| 0.625 | 2 | 13 |

| 0.75 | 3 | 15 |
| 0.875 | 3 | 18 |
| 1.0 | 4 | 20 |

実装では、書体の基準線と字形の墨の範囲（書体の字幅の表にある）から同じ値を出し、`spec/` に倍率ごとの補正として持つ。

## G. ゲームの書体とゲームの UI の版（案 C を土台に 3 つ）

### G.0 前提

#### G.0.1 書体

- 字は全て、ゲームが本文に使う書体（Garden_msg_size16）で描く。ゲームは書体を 4 つの枠に読み込んでいて（本文・ふりがな・数字・16 画素の数字）、実行時にその本文の書体を借りる。書体のファイルも字形も Git に入れない。美咲ゴシックと PixelMplus は、この版では使わない。
- 本文の書体の寸法（倍率 1.0）: 1 字の枠 17×24、行送り 24、基準線は行の上から 18、全角の送り 16、数字の送り 12、半角の空白 6、`+` 12。字形は滑らかで（ドット絵ではない）、ゲーム自身も縮めて使うので、倍率は整数でなくてよい。
- 使う倍率:

| 用途 | 倍率 | 全角の送り | 備考 |
|---|---|---|---|
| 行の名前・値、選択の枠、確認の問い | 0.75 | 12 | 行の上端 + 2 に字の行の上端を置く |
| 説明・題・下の帯・親の列 | 0.6875 | 11 | 説明の行送りは 14 |
| スイッチ・ボタンの中（ON・OFF・待機・実行 など） | 0.625 | 10 | 短い字だけ。読めるかは実機で確かめる（0.625 以下はつぶれやすい） |

#### G.0.3 色の付け方

ゲームの画像はほとんどが白と灰の濃淡で、ゲームはそれをマテリアルの「黒の色・白の色」で塗っている。gohan では次のどちらかにする。

- **推奨: 生成時に焼き込む**。SD の資源の生成器が、`spec/` の色（黒の色・白の色）で塗った RGBA の画像をアトラスに書く。描くときは頂点色を白（フェードの時は不透明度だけ下げる）にする。今の部品（1 つのマテリアルと頂点色）のままで描ける。色を変えたら SD の資源を作り直す。
- 実行時に塗る: 色の組ごとにマテリアルを作り、黒の色と白の色を入れる。色の組は GC1 で十数。SD の資源は色によらないが、板ごとにマテリアルを切り替える費用が増える。

### 0.2 ドット絵をにじませない条件

旧版が実機で確かめた事実をもとに、寸法の決め方の規則にする。

| 規則 | 理由 |
|---|---|
| 画像は等倍で置く。拡大するときは整数倍だけ（字の 2 倍など） | 最近傍で 1.25 倍や 1.75 倍にすると、元の 1 画素が 1 画素と 2 画素に割れて線の太さがばらつき、点々のノイズになる |
| 伸ばすのは、伸ばす向きに一様な部分だけ（9 分割の辺と中、横 3 分割の中） | 角や模様を伸ばすと丸さと模様が崩れる。一様な部分は伸ばしても見た目が変わらない |
| 模様と破線は繰り返しで描く（UV を 1 を超えて指定し、テクスチャは繰り返しにする） | 長さが変わっても点の間隔が変わらない |
| 置く位置・大きさ・動きの途中の位置は、整数の画素に丸める | 半画素の位置は、左右の端が 1 画素ずれて見える |
| テクスチャの読み方は最近傍（補間しない） | 補間すると境目がぼやける |
| 自前のテクスチャを使った後は、テクスチャの設定を元に戻す | 戻さないと、ゲームの側のフェードなどが乱れた |
| 上画面の 3D は、メニューを画面の面（左右の目でずれ 0）に置くのを既定にする。ずらすときも左右とも整数の画素だけずらす | 左右の目で位置が半画素違うと、字が太って見える |

### 0.4 ボタンの印（ゲームの書体）

- 美咲ゴシックにはボタンの印が無いので、ボタンの印の所だけゲームの書体（ゲームのメッセージと文字の部品が使う 16 画素の書体）の私用領域の字で描く。実行時にゲームがメモリに読み込んだ書体を借り、書体のファイルも字形の画像も Git に入れない。

### 0.5 選択中の行の模様（ゲームの背景のテクスチャ）

1. **使うテクスチャ**: ゲームの下画面のメニュー（持ち物などの画面）の背景の 11 枚のうち、`my_mvm_check`（64×64）。16 画素の四角の市松に細かい砂目が乗った物で、
   - 見本 1 の「選択中の帯の市松模様」に一番近い。
   - ほかの 10 枚は、物の形（本・吹き出し・かばん・猫など）が描かれていて、字の後ろに置くと読みにくい。
   - 種類の切り替えの最初の絵で、ゲームの中で一番よく見る。
   背景の 11 枚は、手元の ROM の展開物（無印の romfs の `Layout/Menu/mvmnt_undscrn.arc`）で確かめた。更新の romfs には無い。
2. **緑への補正**: テクスチャを輝度だけの画像にして、色は頂点色で付ける。
   - 作り方: 輝度 `0.299R + 0.587G + 0.114B` を、元の最小〜最大が 0.72〜1.0 になるように伸ばし、16 段（4 ビット）に丸めて、輝度と不透明度の画像（LA4、64×64 で 4,096 バイト）にする。
   - 色: 頂点色を掛ける。案 A・C は `#8AD468`（一番暗い画素が `#63994B`、一番明るい画素が `#8AD468`）。案 B は `#9FE6B4 / 0.9`。
   - 比べた別の方法: (a) 頂点色だけで元の橙を緑にする掛け算（`#8CFFAF`）は、橙と黄の差が緑の濃淡にならず、濁る。(b) マテリアルの黒と白の色で各色を直線で写す方法は、赤と青を緑に変えられない。(c) TEV で G を 3 色に複製して 2 色の間を補間する方法は、市松の半分（G の差が小さい四角）が消える。(d) 輝度＋頂点色（採用）は、字形のアトラスと同じ「白の画像×頂点色」の形で、色を `spec/` の 1 つの値で変えられる。
3. **アニメーション**: ゲームの背景のループは、テクスチャの平行移動 S と T を同時に -0.5 から 0.5 へ、125 フレームで動かす（直線。1 周で 1 タイル＝64 画素、斜めに流れる）。テクスチャは 1 テクセル＝1 画素で貼られている（432 画素の板に 6.75 回）。
   - ゲームのアニメーションのファイルをそのまま結び付ける方法: 同じ動きが保証されるが、自前の板は手で組み立てていてレイアウトのファイルから作っていないので、ゲームのアニメーションの仕組み（アニメーションの資源・結び付け・毎フレームの進め方）を自前の板へつなぐ解析と実装が要る。アニメーションのファイルも romfs から読む必要がある。
   - 同じ値を gohan の設計値として持つ方法（**推奨**）: 仕組みは同じ（テクスチャの座標を一定の速さで流す）で、値もゲームと同じ（125 フレームで 1 タイル、S と T を同時に）。毎フレーム、板の UV に `位相 = floor(経過フレーム × 64 / 125) mod 64` 画素を足すだけで、今の部品（板ごとに UV を書いている）に新しい仕組みは要らない。位相は整数の画素に丸め、模様は画面に固定する（帯が動いても模様は動かず、帯の窓から見える）。
   - 1 フレームの長さは未確認（ゲームが 2D のアニメーションを 30 fps で進めるなら 1 周 4,167 ms）。ゲームの下画面のメニューの背景と並べて実機で合わせる。
4. **テクスチャの置き場所**: ゲームの資源なので Git に入れない。
   - **推奨: SD の資源として生成する（区分 C）**。生成器が利用者の ROM の展開物（無印の romfs）から arc を読み、`my_mvm_check` を展開（ETC1）→輝度→LA4 にして `out/sdmc/` へ書く。3gx は起動時に SD から読む。gohan の中に arc と ETC1 を読むコードが要らず、3gx は ROM 無しで作れる。無印の romfs の場所を `gohan.local.toml` に足す（今は更新の romfs だけ）。
   - 実行時に romfs から自分で読む方法: SD の手順は要らないが、arc と bclim（ETC1）の読み込みを 3gx に入れ、ゲームのファイルの読み方の解析が要る。
   - ゲームが読み込んだ物を借りる方法: 背景はゲームの下画面のメニューを開いている間しか読み込まれていないので、使えない。
   - SD に無い時は、模様の無い一様な緑（頂点色だけ）で描く。見た目以外は変わらない。
5. **プレビューの道具**: `gohan.local.toml` の無印の romfs から同じ arc を読み、同じ輝度化と頂点色で描く。ループは 0・31・62・93 フレーム目のように位相を変えて並べる。ROM が無ければ一様な緑で描く。出力の画像は Git に入れない。

## 5. 決めること・確かめること

- GA1 で進めてよいか、変えたい所。ホットキーの印のパターン（GA.6。既定 H1）。
- 上画面の文字の枠の数（ゲームの版では 64 を推奨。GC1 は通知が重なると 52 になる）。
- ゲームの UI の画像に色を焼き込むか、実行時にマテリアルで塗るか（G.0.3。推奨は焼き込み）。
- ゲームの書体の 0.625 倍（スイッチの中の字）と 0.6875 倍（説明・帯）が実機で読めるか。読めなければ 0.75 に上げ、スイッチを幅 50 にする。
- ゲームのレイアウトの窓の部品を使えるか（使えれば窓 1 つが板 9 枚から 1 つになる）。
- 上画面の板の数（推奨 128）と、矩形・画像・繰り返しを 1 つの数で持つか別に持つか。
- 3 分割のスイッチ（3 枚）を、長い帯から 2 枚切り出す形に減らすか（幅の上限はアトラスの幅 256）。
- ゲームの書体を自前の文字の部品で使うための、ゲームが読み込んだ書体（4 つの枠）の場所。名前と型を付ける作業が要る。
- 8 画素のボタンの印（実行時に 2×2 の平均で作る）が読めるか（実機）。
- 模様の流れる速さ（ゲームの下画面のメニューの背景と並べて実機で合わせる）。
- 左右の目のずらし量を自前の描画に使えるか（案 B・C の奥行き）。
- プレビューで背景を確かめる場合は、任意の RomFS のルートを `gohan.local.toml` に指定する（更新を優先し、読めなければ本体を使う）。
