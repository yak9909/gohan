# ゲームへの入力の遮断

状態: 段 1・2 と段 4 の要求生成まで実装（2026-10-22）。フックは未実装で、ゲームへの遮断はまだ働かない。対象は日本版（無印＋更新）。

メニューを開いている間、メニューの操作（十字・A・B など）がゲームにも届き、操作のたびにゲームが動いてしまう。これを止めるため、ゲームが入力を読む途中に入り、ゲームへ渡す入力から取り除く。遮断は今後、メニュー・文字入力・キーの割り当て・エディター・ホットキーなど多くの機能が同時に使うので、機能ごとの特別扱いにせず、重ねて使える汎用の部品として設計する。

「メニューはどの場面でも開ける」は変えない。遮断を導入できなくても、メニューは開き、操作できる（ゲームにも届くだけ）。

---

## 0. 要約

| 項目 | 決めた事 |
|---|---|
| 場所 | ゲームの入力の流れの 2 か所にフックを入れる。(P) パッドを読む関数の中（SELECT を START に読み替える前）で SELECT を消す。(C) コントローラーの計算の中（生入力を読んだ直後・押した/離したを作る直前）で、遮断する区分を消し、旧状態も揃える。 |
| 方式 | コードを書き込む方式（旧版のケーブ）をやめ、毎フレームのフックと同じ CTRPF の Hook と、`src/game/` の自前の関数で行う。元の命令はフックが保存・復元する。 |
| 境界 | 遮断の開始の瞬間に離しを出さず、終了の瞬間に押下を出さない。終了後も押されたままの入力は、離すまでゲームへ渡さない（掛かり）。 |
| API | 所有者ごとに要求（遮断する区分・押し切るボタン）を持ち、有効な遮断は全員の和集合。区分はボタン単位 + スライドパッド + タッチ。持続する要求で、毎フレーム頼み直さない。 |
| 層 | 要求の表と区分は `core`、遮断の規則（純粋な関数）とフックは `game`、メニューの要求は `menu` が作り `features` が表へ置く。 |
| 既定 | メニュー（ダイアログ・入力の枠を含む）が開いている間はボタン・十字・START を遮断。SELECT は常に遮断。スライドパッドとタッチは通す。押し切りの既定は START だけ（旧版と同じ）。 |
| 失敗時 | フックごとに独立に導入し、失敗は状態に残す。失敗してもメニューは開く。要求は受け付け続け、効果が無いだけ。 |
| PC の試験 | 表と規則は純粋な関数なので、フレームごとの入力列から「ゲームが見る押下・離し」を PC で出し、不変条件を乱数でも確かめる。 |

旧版の実績と、旧版のどこを引き継ぎ・変えるかは 9 節にまとめた。

## 1. 範囲と用語

**含む**: ゲームが読む入力（ボタン・十字・スライドパッド・SELECT・START・タッチ）をゲームへ渡さないこと、その要求の重ね方、開閉の境界の扱い、押し切り（押している間は渡さず、離した時に 1 回の押下として渡す）。

**含まない**:
- gohan 自身が読む入力。メニュー・ホットキー・機能は CTRPF の `Controller`・`Touch`（OS の入力を直接読む）から読むので、遮断の影響を受けない。
- 機能どうしの入力の取り合い（どの機能が操作を受け持つか）。遮断は「ゲームへ渡さない」だけを決める。
- ゲームの部品へ入力を渡すこと（旧版のエディターは、ゲームの一覧の部品に自分で十字・A を渡していた）。遮断中でも妨げないが、渡す仕組みは別に設計する。
- カメラの停止などの、入力以外の凍結（旧版のエディターはゲームの関数を書き換えていた）。
- タッチの領域指定。遮断は画面全体の入り切りだけ。

| 用語 | 意味 |
|---|---|
| 区分 | 遮断の単位。ZL・L・R・ZR・十字 4 方向・A・B・X・Y・SELECT・START の各ボタン、スライドパッド、タッチ。 |
| 要求 | ある所有者が「この区分をゲームへ渡すな」「このボタンを押し切るまで渡すな」と置く内容。 |
| 所有者 | 要求を置く側（メニュー・エディター・設定など）。名前を持ち、表に枠を 1 つ持つ。 |
| 生の入力 | ゲームがパッドから読んだままの入力（遮断の前）。 |
| 出力 | 遮断の後、ゲームの各部品が見る入力。 |
| 掛かり | 遮断が終わっても、押されたままの入力を離すまで遮断し続けること。 |
| 押し切り | 押している間はゲームへ渡さず、離した時に 1 回の押下として渡すこと。 |

## 2. ゲームの入力の仕組み（確かめた事）

出典は全関数の書き出し（逆アセンブル・擬似コード）と、バイト列の読み出し。確かさは「静的」（コードを読んだ）と「実機」（旧版で動かして確かめた）を分けて書く。番地は日本版 v1.5 のもの。実装では `spec/game_api.toml` から生成する。

### 2.1 入力の流れ

```
OS の入力（HID）
  ├─ CTRPF の Controller・Touch はここを直接読む ……… 遮断の影響を受けない
  ▼
[1] 装置の更新           0x0053F550（CtrHidDevice の calc）
      ├ パッドを読む関数  0x003533D0（以下「パッド読み」）
      │    装置の欄 +0x15C0 へ { 保持, 押した, 離した, スライドパッド x/y }
      │    途中で前回の保持を保存 → 条件付きで SELECT を START に読み替え（0x00483020）
      └ タッチ読み        0x00352514（装置の欄 +0x15D4 へ）
  ▼
[2] コントローラーの計算  sead::Controller::calc  0x0053CDC4（CtrController）
      a. 旧い保持 R8・旧い有効旗 R9 を退避
      b. 装置の欄から保持・タッチを読む         0x00540870
      c. 押した/離した/リピートを作る           0x00542E88
      d. 登録された Wrapper に同じ旧状態を渡す  0x005475D4
  ▼
ゲームの各部品（Wrapper の欄を読む部品 / 先頭のコントローラーを直接読む部品 / 共有のタッチ状態）
```

[1] の装置の更新が先、[2] のコントローラーの計算が後（0x005404AC が、装置を仮想関数で更新してからコントローラーを更新する）。静的。

### 2.2 パッド読み（0x003533D0）

- 引数は読み手（R0、関数の中では R5）とパッド構造体（R1、関数の中では R4）。パッド構造体は `+0 保持 / +4 押した / +8 離した / +0xC,+0xE スライドパッド x/y（16 ビット）`。
- 0x003534C8 で `LDR R0,[R4]`（保持を読む）、直後の 0x003534CC で `STR R0,[R5,#8]`（前回の保持として保存）。読み替えの前の、素の保持が保存される。
- 続く 0x003534D0〜0x003534E0 で、0x009778D8 のバイトが 0 のときだけ `BLEQ 0x00483020`（SELECT を START に読み替える）。0 でなければ読み替えは行われない。0x003534D0 の `LDR R0,=…` は PC 相対なので、ここは元の命令をそのまま再現できる場所ではない。
- 保持のビット 13（0x2000）は 0x00353470 で常に捨てられる。
- パッド構造体の欄を読むのは、コントローラーの装置読み（0x00540870）だけ（欄の位置を直接使う命令の検索の範囲）。そこで使うのは保持の語とスライドパッドの値（+0xC,+0xE）だけで、押した/離したの語は読まれない。したがって、ゲームへ届く入力は保持の列で決まる。

### 2.3 SELECT の読み替え（0x00483020）

- 保持に SELECT（ビット 2）があれば、それを消して START（ビット 3）を立てる。押した/離したからも SELECT を消す。START の押した/離したは、SELECT との同時押しの規則で作り直される。
- つまり、読み替えの後は SELECT と START を区別できない。SELECT だけを消して START を残すには、**読み替えの前**に SELECT のビットを保持・押した・離したの 3 語から消せばよい（元の ARM を CPU で動かし、新旧の SELECT/START 全 16 通りで確認した記録がある。実機ではない）。
- 読み替えが行われない経路（上のバイトが 0 でない）では、SELECT は読み替えられず、下流にコントローラーの SELECT（0x1000）として届く。

### 2.4 コントローラーの計算（0x0053CDC4）と欄

呼び出しの順は次のとおり（0x0053CDC4）。

1. 0x0053CDD0: 旧い保持 `R8 = [self+0x110]`。0x0053CDD4: 旧い有効旗 `R9 = [self+0x10] & 1`。
2. 0x0053CDE4: 仮想関数（CtrController の仮想表 0x008FE6F8 の +0x18、実体は 0x00540870）で、保持・タッチを読み込む。
3. 0x0053CDE8〜0x0053CDF4: `R2=R9`、`R1=R8`、`R0=self` を揃えて `BL 0x00542E88`（押した/離した/リピート/保持フレーム数/タッチの現れた・消えたを作る）。
4. 後半（0x0053CE84〜0x0053CE90）で、登録された Wrapper の仮想関数（+0x10、実体は 0x005475D4）を、**もう一度 R8・R9 から** `R1=R8`、`R2=R9` として呼ぶ。

CtrController の仮想表は 0x008FE6F8（+0x10 に calc、+0x18 に装置読み、+0x1C に入力なしの判定）。実際のバイトで確かめた。calc を使うのは CtrController だけ。

| 欄（self からの位置） | 意味 |
|---|---|
| +0x04 / +0x08 / +0x0C | 押した / 離した / リピート |
| +0x10 | タッチの旗。ビット 0 有効、1 現れた、2 消えた、3 座標リセット |
| +0x14 / +0x18 | 画素座標（整数） |
| +0x2C + 4i | ボタンごとの押し続けフレーム数 |
| +0xFC | ボタン数 |
| +0x100 / +0x104 | 軸からボタンへの開始番号。CtrController では両方 -1（軸からの再生成は無い） |
| +0x108 | タッチが使う保持のビット番号（15） |
| +0x10C | 入力なしのフレーム数 |
| +0x110 | 保持 |
| +0x114 / +0x118 | 画素座標（実数） |
| +0x11C / +0x120 | スライドパッドのアナログ x / y |

### 2.5 押した/離したの作り方と、旧状態

0x00542E88 は `押した = 新 & ~旧`、`離した = 旧 & ~新`、押し続けフレーム数、リピートを作る。旧は引数（R8）で、前回の最終的な保持と同じ値。タッチの現れた/消えたも、新旧の有効旗（R9）の差から作る。

したがって、**現在の保持だけを消すと、前のフレームで押されていたボタンは離したとして出る**。旧状態も消さないと、遮断の開始の瞬間に離しが出る。しかも旧状態は 2 か所で使われる（本体への呼び出しと、Wrapper への呼び出し。後者は R8・R9 から作り直す）ので、`BL 0x00542E88` の引数だけを直しても足りず、**R8・R9 そのものを揃える**必要がある。揃える位置として、0x0053CDE8（`MOV R2,R9` の位置、calc の先頭から +0x24）が使える。ここで生入力は読み終わっていて、押した/離したの計算はまだ。静的。元の ARM の CPU 実行で、本体・Wrapper とも離しが出る例と、R8/R9 を 0 にすると出なくなる例を再現した記録がある（実機ではない）。

### 2.6 Wrapper と直接の読み手

- Wrapper（0x005475D4）は、先頭のコントローラーの保持を表（Wrapper の +0x174）で組み替え、旧状態も同じ表で変換して、自分の押した/離したを作る。タッチは有効旗と座標を複写する。
- ゲームの部品の中には、Wrapper を介さず、管理体の先頭のコントローラーの保持を直接読むものがある（0x00304A44）。共有のタッチ状態の更新（0x001B7874）やスクロールバーはこれを使う。**Wrapper だけを遮断しても足りず、コントローラー自身を変える必要がある**。静的。

### 2.7 タッチの二重の表現

タッチは 2 系統で表される。

1. 有効旗（`+0x10` のビット 0）と画素座標。
2. 保持の中のビット（`1 << [+0x108]`、実機のコントローラーでは 15、すなわち 0x8000）。

`SetPointerState`（0x00542D78）が両方を書く。有効旗だけを落とすと、保持の中のビットが残る。旧版の実機で、左上に幻のタッチが出た（旧版の記録。デバッガ版で観測）。さらに、新旧の有効旗の差からタッチの現れた/消えたも作られるので、旧い有効旗（R9）も揃える。座標の値は有効旗が偽でも消えない（読み手が有効旗を先に見る前提。実機未確認）。

装置の接触欄（`+0x15D4`）を読むのは、コントローラーの装置読みだけ（検索の範囲）。

### 2.8 スライドパッド

スライドパッドは 2 系統。方向のビット（保持の 0x00F00000）と、アナログ値（`+0x11C`/`+0x120`）。ビットを消してもアナログ値は残り、Wrapper もそのまま複写する。完全に止めるには両方を消す。旧版の「常に許可」は、実機で動いた（デバッガ版）。

遮断の規則がスライドパッドを「押している」と見なす条件は、**方向のビット（保持の 0x00F00000）だけ**。アナログ値は押している判定に使わない。中央に戻してもアナログ値がちょうど 0 になるとは限らず、小さな値が残っても方向のビットは立たないため、アナログ値を判定に入れると、遮断が終わった後の掛かり（4.3 手順 2）が離しても解けなくなる。遮断している間のアナログ値の 0 化（4.1 の出力）は、判定とは別にそのまま行う。

### 2.9 ビットの対応

パッドの語のビット（パッド読みで見えるもの）と、コントローラーの保持のビット。名前は旧版・既存の調査の対応による。ZL の対応は実機で確かめていない。ZR に当たるビットは無い（パッド読みでビット 13 が捨てられ、保持の組み替え表にも無い）。

| 区分 | パッドの語 | コントローラーの保持 |
|---|---|---|
| A | 0x0001 | 0x00000001 |
| B | 0x0002 | 0x00000002 |
| SELECT | 0x0004 | 0x00001000 |
| START | 0x0008 | 0x00000800 |
| 十字 右 / 左 / 上 / 下 | 0x0010 / 0x0020 / 0x0040 / 0x0080 | 0x00080000 / 0x00040000 / 0x00010000 / 0x00020000 |
| R / L | 0x0100 / 0x0200 | 0x00004000 / 0x00002000 |
| X / Y | 0x0400 / 0x0800 | 0x00000008 / 0x00000010 |
| ZL（推定） | 0x1000 | 0x00000080 |
| スライドパッド 右 / 左 / 上 / 下 | ビット 28 / 29 / 30 / 31 | 0x00800000 / 0x00400000 / 0x00100000 / 0x00200000 |
| タッチ | （接触の別の欄） | 有効旗 + 0x00008000 |

**SELECT / START の食い違いの確認**: 旧版 v1 の文書は SELECT=0x800 を実測、START=0x1000 を推定としていたが、保持の組み替えを読むと逆である。0x00540870 の装置読みは、0x00540938〜0x0054094C でパッドの `0x8`（START）を保持の `0x800` に、0x00540A28〜0x00540A3C でパッドの `0x4`（SELECT）を保持の `0x1000` に移す。上の組み替え表はこの命令列と一致するので、**SELECT=0x1000、START=0x800 を採用**する。旧版の SELECT の実測値 0x800 は、上流の 0x00483020 で SELECT を START に読み替えた後を観測した可能性が高い。これは旧版の測定位置が不明なため推論であり、新たな実機測定ではない。

コントローラーの保持で何にも割り当てられていない下位のビット（0x00000764）は、遮断の対象にもしない（触らない）。

### 2.10 1 フレームの順序と実行するスレッド

ゲームのメインループは、1 周で calc → draw の順に進み、論理と描画を別の周期で回す仕組みは無い（既存の調査）。毎フレームのフック（`Frame_DrawPass1024` の中、描画側）は、同じ周の calc の後に呼ばれる。つまり、**ある周の描画側（FrameStep）で置いた要求は、次の周の calc から効く**。1 フレーム（30fps で約 33ms）の遅れは避けられない。

パッド読みとコントローラー計算が同じスレッドで動くことは、呼び出しの木（0x005404AC が装置→コントローラーの順に呼ぶ）から読める。FrameStep が同じスレッドかは、静的には裏付けが弱い。設計は「別のスレッドでも正しい」形にする（要求の表は待たない受け渡し）。

### 2.11 CTRPF の側

- CTRPF の `Controller` は OS の入力を直接読む。ゲームの入力を変えても、CTRPF・gohan のメニューの入力は変わらない。
- CTRPF のメニューは既定の開く操作が SELECT。開くと `OnOpening`（gohan では `ShouldOpenCtrpfMenu`）を呼び、続けてゲームのプロセスを止める（`Pause`）。閉じると再開する。閉じる経路のうち `OnClosing` が呼ばれるのは開く操作で閉じる場合だけで、メニューの中の操作（B など）で閉じる場合は呼ばれない。
- CTRPF は、押されているキーの値が Rosalina の呼び出しの組み合わせ（OS の設定から `svcGetSystemInfo` で読む）に一致する間は、自分のメニューを開かない。
- Hook は元の命令を保存し、`B` で CTRPF の呼び出し台（0x01E80000 付近）へ飛ぶ。台は呼び出し元レジスターを保存して `blx` でコールバックを呼ぶ。条件付きの `BL`（`BLEQ`）や PC 相対の `LDR` は、元の命令を実行する指定（`EXECUTE_OI_*`）では扱えない（CTRPF の Hook が拒否する、または誤った位置へ飛ぶ）。

## 3. 遮断の場所と方式

### 3.1 決定

| 対象 | 場所 | 内容 |
|---|---|---|
| SELECT | **フック P**: パッド読みの 0x003534C8（関数の先頭から +0xF8、`LDR R0,[R4]`） | パッド構造体の保持・押した・離したの 3 語から SELECT（ビット 2）を消す。生の SELECT の押下状態を遮断の状態に記録する。 |
| ボタン・十字・START・スライドパッド・タッチ・押し切り | **フック C**: calc の 0x0053CDE8（先頭から +0x24、`MOV R2,R9`） | 生の入力を区分に分け、遮断の規則（4 節）を適用して保持・有効旗・アナログ値と、R8・R9 を書き換える。 |

**P をここにした理由**
- 0x003534C8 は、読み替えの有無で分かれる 2 経路が合流した後で、条件分岐（0x009778D8 のバイト）の前にある。どちらの経路でも SELECT を消せる。旧版は条件付きの `BLEQ`（0x003534E0）に入れたため、バイトが 0 でないとき SELECT 遮断も押し切りも働かなかった（旧版の記録にも「条件の間だけ効く」とある）。
- 前回の保持を保存する `STR R0,[R5,#8]` より前なので、元の命令（`LDR R0,[R4]`）の結果は素の保持のまま保存される。コールバックが R0 を保存して返せば、保存される値は素の保持（読み替え前の SELECT を含む）で、読み手の履歴は元のゲームと変わらない。
- 元の命令が PC 相対でも条件付きでもないので、毎フレームのフックと同じ標準の指定（元の命令を先に実行してからコールバック）で入れられる。0x009778D8 のバイトの意味は分かっていない（書き手・場面ごとの値は未追跡）ので、このバイトに依存しない。

**C をここにした理由**
- 生入力を読んだ後・押した/離したを作る前なので、ここで保持を削れば押した/離した/リピート/押し続けフレーム数は削った値から作られる。
- R8・R9 は後半の Wrapper 呼び出しにも使われる。0x0053CDE8 は R8・R9 をレジスターのまま書き換えられる最後の位置。`BL 0x00542E88` の位置（旧版）では R1・R2 は直せても、Wrapper に渡す R8・R9 が旧いままになる。
- 元の命令（`MOV R2,R9`）をコールバックの後に実行する指定（`EXECUTE_OI_AFTER_CB`）にすれば、書き換えた R9 が引数に入る。PC 相対ではない。
- この位置では R0〜R3・R12・VFP の呼び出し側保存の部分は使われていない（次の命令が R2・R1・R0 を作り直し、直後に `BL`）。それでも、コールバックの契約は R8・R9 以外の全レジスターを保存して返す、とする（7.1）。

### 3.2 コードを書き込む方式（旧版のケーブ）にしない理由

旧版は、ゲームの未使用領域（0x00838020 付近）に手で組んだ機械語を書き、2 か所の命令を差し替えていた。この版では、毎フレームのフックと同じ CTRPF の Hook と、コンパイルした関数を使う。

- 機械語の即値の誤り（`BIC #0x800` を手で書いて `#0x200` になっていた）を、旧版は逆アセンブルの検査で捕まえていた。コンパイラに任せればその種の誤りが無い。
- 未使用領域が本当に空きかを実行時に確かめる必要が無い。
- 取り外しは Hook が元の命令を復元する。旧版は、フックを戻した直後にケーブをゼロで埋めていて、実行中のスレッドがケーブにいると未定義の命令に落ちうる作りだった（コードの読み。実機では観測していない）。
- 代わりの危険: CTRPF の Hook は呼び出し台で CTRPF 用の領域（スレッドごとのローカル領域の +0x3C）を使う。ゲームがそこを別の用途に使っているスレッドでは、CTRPF が異常を検出してエラーを出す（Hook の実装）。毎フレームのフックは同じ仕組みで実機で動いているが、パッド読みと calc のスレッドで同じかは未確認（12 節）。

### 3.3 分けて行う理由

- SELECT は読み替えの後では START と区別できないので、パッド読み（P）でしか消せない。
- それ以外は P でも保持を削れるが、押した/離したはコントローラーが旧状態から作り直すので、P では離しを隠せない。タッチは別の欄から読まれ、P では触れない。よって C で行う。
- C は SELECT も扱える（コントローラーの SELECT は 0x1000）。P が入らず、読み替えが行われない経路のときの保険として、C でも SELECT の区分を消す。P が入らず読み替えが行われる経路のときは、SELECT は START として届く（防げない。状態表示に出す）。

## 4. 遮断の規則（状態の遷移）

遮断の中身は、ゲームのメモリに触れない純粋な関数 `Step(状態, 入力, 出力)` にする。`src/game/` に置き、PC で試験する。フック C の関数は、ゲームのメモリから入力を読み取り、この関数を呼び、結果を書き戻すだけ。

### 4.1 入力と出力

| 入力 | 内容 |
|---|---|
| 生の保持 | 区分の集合。コントローラーの保持と有効旗から作る（2.9 の表）。スライドパッドの区分は方向のビットだけで決め、アナログ値は見ない（2.8）。P が入っていれば SELECT は含まない。P が入っておらず読み替えが行われない経路では SELECT（0x1000）が現れうるが、SELECT は常に遮断対象なので同じ規則で消える。 |
| 旧い保持・旧い有効旗 | R8・R9。前回ゲームへ渡した値。 |
| 遮断の要求 | 有効な `block`（遮断する区分）と `defer`（押し切るボタン）の和集合（5 節）。SELECT は常に含まれる。 |
| SELECT の物理状態 | P が記録した、今フレームで SELECT が押されているか。 |
| 時刻 | ミリ秒（押し切りの窓と中断の検出に使う）。 |
| CTRPF 再開 | 開く通知を記憶し、メニューが閉じた後の最初の入力計算へ一度だけ渡す明示的な知らせ。 |

| 出力 | 内容 |
|---|---|
| 保持・有効旗 | 書き戻す値。遮断する区分のビット、タッチなら有効旗と保持のビット 15 を落とす。 |
| アナログ値の 0 化 | スライドパッドを遮断するとき、`+0x11C`/`+0x120` を 0 にする。 |
| 新しい R8・R9 | 遮断する区分のビットを落とした旧状態。 |

### 4.2 状態

`掛かり`（遮断が終わっても離すまで遮断する区分）、`保留・窓・通過`（押し切りの 3 つの集合）、窓の開始時刻、前回の生の入力、前回の時刻、中断の待ち受けの残り。ゲームのスレッドだけが読み書きする。

### 4.3 1 回の手順

1. **中断の待ち受け**: CTRPF 再開の知らせがあれば、時間や SELECT に関係なく、押されているボタン・十字・START・タッチを掛かりに加え、押し切りの状態を捨てる。通知の無い Rosalina 用には、SELECT を見た後の 30 呼び出しだけ待ち受け、前回から 100ms 以上空けば同じ処理をする。判定は今回の SELECT による待ち受け更新より先に行い、SELECT の無い長い周期の末尾で初めて SELECT が押された場合を誤検出しない。
2. **遮断する区分**: `block` に、SELECT が押されているならボタン・十字・START（SELECT の保護）を加える。これに「掛かり ∩ 生の入力」を足したものが、今フレームの遮断。次の掛かり = 今フレームの遮断 ∩ 生の入力。
3. **押し切り**（`defer`）: 遮断されたボタンの保留・窓・通過は捨てる。遮断されていない `defer` のボタンについて、旧版と同じ規則を行う（4.5）。
4. **出力**: 生の入力から遮断する区分と押し切り中のボタンを除き、窓のボタンを足す。有効旗・保持のビット 15・アナログ値は区分に従って書く。
5. **旧状態**: 旧い保持・旧い有効旗から、遮断する区分を落とす。

### 4.4 開く・閉じるの境界

手順 2 と 5 により、次が成り立つ。

| 場面 | ゲームが見るもの |
|---|---|
| 遮断の開始の瞬間に A が押されたまま | 保持が 1 → 0 になる。**離しは出ない**（旧い保持からも落とすため）。 |
| 遮断中にボタンを押す・離す | 何も出ない。 |
| 遮断の終了の瞬間に A が押されたまま | **押下は出ない**。離すまで保持は 0 のまま（掛かり）。離した後は何も出ない。 |
| 遮断の終了の瞬間に A は離れている | 何も起きない。 |
| 遮断していない区分 | 生の入力と同じ。押下・離しとも素通し。 |

A を押したまま、4 フレーム目から 5 フレーム目の終わりまで遮断した例（検算に使ったモデルの出力。要求が効くフレームを直接書いた）。

```
フレーム  生の A  遮断   ゲームの保持  押した  離した
   1        -     -        -          -       -
   2        A     -        A          A       -
   3        A     -        A          -       -
   4        A     ボタン   -          -       -    ← 離しを隠す
   5        A     ボタン   -          -       -
   6        A     -        -          -       -    ← 押下を隠す（掛かり）
   7        A     -        -          -       -
   8        -     -        -          -       -    ← 離すと掛かりが終わる
```

離しを渡す案（遮断の開始に 4 フレーム目で離しが出る）は選ばなかった。利用者の条件が「押したままのボタンが押下・離しとして届かない事」であり、保持の水準が 0 になれば水準で動くゲームの処理は止まる。離しの出来事を待つゲームの部品が止まったままになる可能性は、実機で確かめる（12 節）。確かめた結果で差し替えられるよう、離しを隠すか否かは定数 1 つにする（`kHideReleaseOnBlock`、既定は隠す）。

### 4.5 押し切り（旧版から引き継ぐ）

`defer` に入れたボタンは、押している間ゲームへ渡さず、離した時に 1 回の押下として渡す。START+十字上のようなホットキーで、ゲームがセーブの窓などを出さないための機能。規則は旧版と同じ。

- 押し始めの時点でほかのボタン（ボタン・十字・START・SELECT。スライドパッドとタッチは数えない）が押されておらず、離すまで混ざらなかったときだけ、離したフレームに押下を渡す。混ざったら取り消す。
- 渡した押下は 300ms 押したままにする（窓）。窓の間に同じボタンを押し直したら、押下を出さずにそのまま通す（長押し。離すまで）。押し直さなければ 300ms で離しを出す。
- 窓は 1 本。別のボタンの押下を渡すと、前の窓は同じフレームで離す。

旧版との差: 遮断との整合を入れた。遮断（メニューなど）が掛かっているボタンは、保留・窓・通過を捨てる。メニューの中で START を押して離しても、メニューを閉じた後に遅れて START が届かない。時間の測り方は、旧版がケーブの中でシステム時計を読んでいたのに対し、`Step` への引数にする（試験のため）。

押し切りの出力は保持の列として書けばよく、押した/離したはコントローラーが作る。パッド構造体の押した/離したの語は、この規則では作らない（読む部品が無い。2.2）。

### 4.6 SELECT の保護

SELECT が物理的に押されている間は、ボタン・十字・START も遮断する。SELECT を使う操作（gohan のメニューの開閉、CTRPF のメニュー、Rosalina の呼び出し）の組み合わせの相手のボタンが、ゲームへ漏れないようにする。スライドパッドとタッチは遮断しない。SELECT の保護が終わった後、押されたままのボタンは掛かりで離すまで渡さない。

SELECT 自身は、要求とは関係なく常に遮断する（P）。これは「SELECT 用の要求」を恒常的に持つ内蔵の所有者で表す（5.2）。

### 4.7 中断

CTRPF のメニューや Rosalina の画面でゲームが止まっている間に押されたボタンは、再開時に新しい押下になりうる。再開の最初の入力計算で、押されているボタン・十字・START・タッチを掛かりに加え、押し切りの保留・窓・通過を全て捨てる。スライドパッドは中断による掛かりの対象にしない。

- **CTRPF は通知を使う**。`ShouldOpenCtrpfMenu` / `OnOpening` が開くことを許可した時に開く通知を記憶し、CTRPF の `Process::OnPauseResume(false)` で再開の知らせを `core` の待たない受け渡しへ置く。この通知は `ProcessImpl::Play` が `ResumeFrame` する前に呼ぶので、閉じた後の最初の入力計算で `ctrpf_resumed` を一度だけ `Step` へ渡せる。`OnClosing` だけには依存しない（2.11 の B などで閉じる経路では呼ばれない）。開く通知は `Pause` より前なので、その通知だけを入力計算で消費せず、再開の知らせを待つ。既存の停止・再開コールバックがあれば呼び出しを引き継ぐ。通知の接続と、競合時にも再開を失わない受け渡しは段 3・4 で試験する。
- **Rosalina だけ時間で推測する**。SELECT を見た後の 30 呼び出しの間に、前回から 100ms 以上空けば中断とみなす。既定の L+下+SELECT を対象とし、SELECT を含まない設定では働かない。
- 長い周期の後に初めて SELECT を見ても、その周期は対象にしない。SELECT の無い通常の読み込みでは掛かりを作らず、走る B などを止めない。待ち受けは 30 呼び出しで終え、中断を検出した時は終了する。

## 5. 汎用 API

### 5.1 区分と要求

```cpp
// src/core/input_block.hpp
namespace gohan::core::input_block {
using Mask = std::uint32_t;

// 区分。ui::input::button と同じ並びに、スライドパッドとタッチを足す。
namespace part {
inline constexpr Mask ZL = 1u << 0, L = 1u << 1, R = 1u << 2, ZR = 1u << 3;
inline constexpr Mask Up = 1u << 4, Down = 1u << 5, Left = 1u << 6, Right = 1u << 7;
inline constexpr Mask A = 1u << 8, B = 1u << 9, X = 1u << 10, Y = 1u << 11;
inline constexpr Mask Select = 1u << 12, Start = 1u << 13;
inline constexpr Mask SlidePad = 1u << 14, Touch = 1u << 15;
} // namespace part

namespace group {
inline constexpr Mask Face = part::A | part::B | part::X | part::Y;
inline constexpr Mask Shoulder = part::L | part::R | part::ZL | part::ZR;
inline constexpr Mask DPad = part::Up | part::Down | part::Left | part::Right;
inline constexpr Mask Buttons = Face | Shoulder | DPad | part::Start; // SELECT・スライドパッド・タッチを含まない
inline constexpr Mask Everything = Buttons | part::SlidePad | part::Touch;
} // namespace group

struct Claim {
    Mask block = 0; // 押している間ゲームへ渡さない区分
    Mask defer = 0; // 押し切るまで渡さないボタン（group::Buttons の部分集合）
    constexpr bool operator==(const Claim &) const = default;
};

struct Effective { // 有効な遮断。ゲーム側が読む
    Mask block;    // 全所有者の block の和集合。part::Select を必ず含む
    Mask defer;    // 全所有者の defer の和集合
    std::uint32_t generation;
};

enum class Result { Ok, Unchanged, Busy, Full, Invalid };

struct Owner { // Table::Acquire が返す。コピー可。枠の番号だけを持つ
    std::uint8_t slot = 0xFF;
};

struct OwnerInfo { // 開発版の状態表示用
    const char *name;
    Claim claim;
};

class Table {
  public:
    // 所有者の枠を借りる。name は静的な文字列（状態表示に出す）。枠は 16 個（core::limits）。
    Result Acquire(const char *name, Owner &owner);
    // その所有者の要求を置き換える（持続する。解除するまで有効）。
    Result Set(const Owner &owner, const Claim &claim);
    // 要求を消して枠を返す。
    Result Release(Owner &owner);

    // ゲーム側。待たない。更新が無いか競合なら前の値のまま。
    MailRead Read(Effective &out, std::uint32_t &generation);

    // 開発版の状態表示用。所有者の名前と要求を数える。
    std::size_t List(OwnerInfo *out, std::size_t capacity);
};
Table &Global();
} // namespace gohan::core::input_block
```

### 5.2 要求の重ね方

- **和集合**: 有効な `block` / `defer` は、全所有者の要求の和集合。2 つの機能が同じ区分を要求して、片方が先にやめても、もう片方の間は遮断が続く。
- **持続**: `Set` は置き換え。解除は空の要求を置くか `Release`。毎フレーム頼み直す必要は無い（5.5）。同じ内容を置けば `Unchanged`。
- **SELECT**: 表の 0 番の枠は、内蔵の所有者 `reserved` が `block = part::Select` で恒常的に持つ。`Release` も書き換えもできない（`Invalid`）。よって有効な `block` は常に SELECT を含み、フック P は要求の有無を見ない。
- **遮断と押し切りの優先**: 同じボタンが遮断と押し切りの両方に入っていれば、遮断が優先し、押し切りの状態は捨てる（4.3 の手順 3）。
- **不正な要求**: `defer` が `group::Buttons` に収まらない要求は `Invalid`（何も変えない）。`block` は何を含んでもよい。
- **導入前・失敗時**: フックが入っていなくても `Set` は受け付ける（効果が無いだけ）。導入が済めば、置かれていた要求が最初のフレームから効く。

### 5.3 スレッドと待ち

どのスレッドからでも `Acquire`・`Set`・`Release` を呼べる。どれも待たない（既存の部品と同じく try-lock）。競合したら `Busy` を返し、**何も変えない**（表と公開値の両方が元のまま）。呼び出し側は次のフレームにもう一度呼ぶ。

実装は次のとおり。所有者の表は書き手どうしの排他（`SpinMutex`）で守り、有効な遮断は `Mailbox<Effective>` で公開する。ゲーム側の `Read` はコピー 1 回で、公開の途中なら前の値で動く。CTRPF が止めたスレッドがロックを持ったままになっても、書き手は待たずに `Busy` で返るので、止まらない。

### 5.4 層の置き場

```
features   メニューの接続（要求を置く）、押し切りの設定、エディターなどの機能
  │
menu       Shell が「今ゲームに渡したくない物」を Claim で返す（InputDemand）
ui         （入力の読み取りは従来どおり。遮断には関わらない）
  │
game       input_filter（純粋な規則 Step。状態表示用の数え上げ）
           input_hook（フック P・C の導入・取り外し、ゲームのメモリとの受け渡し、状態）
  │
core       input_block（区分・Claim・Table）、limits（容量・時間の定数）
```

- `core` は `Table` と区分だけを持つ。ゲームのことは知らない。
- `game` は `core` の `Effective` を読み、規則を適用する。ゲームの欄の位置・ビットの対応・番地は `game` に閉じる。
- `menu` は `core` の `Claim` を使って、メニューが必要とする遮断を返す（`Shell::InputDemand()`。エンジンが開いている、またはダイアログ・入力の枠が出ているとき `{block = Buttons}`、それ以外は空）。`menu` は `Table` を知らない。
- `features/menu_screen` が `Table` に所有者 `menu` の枠を借り、毎フレームの最後で `InputDemand()` を `Set` する。
- 区分のビットの並びが `ui::input::button` と `menu::key` と同じであることは、`features/menu_screen` の `static_assert`（既存の同種の検査の隣）で守る。
- 同列の層（`ui` と `menu`、`menu` と `world`）を結び付けない。

### 5.5 使い方の例

```cpp
// features/menu_screen: Wire で枠を借り、FrameStep の最後で置く
core::input_block::Owner owner;
bool retry = false;

void PublishDemand() {
    const Claim want = shell.InputDemand(); // 開いている間 {group::Buttons}、閉じていれば {}
    if (want == last && !retry) return;
    const auto result = table.Set(owner, want);
    retry = result == Result::Busy;         // 競合したら次のフレームでもう一度
    if (result == Result::Ok || result == Result::Unchanged) last = want;
}
```

| 使う側 | 要求 | いつ |
|---|---|---|
| メニュー（ダイアログ・入力の枠を含む） | `{block = Buttons}` | 開いている間 |
| 座標移動の「十字キーの無効化」 | `{block = DPad}` | ホットキーを押している間 |
| 十字で動かすカーソル | `{block = DPad}` | その機能が有効な間 |
| 文字変換の候補欄 | `{block = DPad}` | 候補が出ている間 |
| 下画面のキーボード・スライダー | `{block = Buttons \| Touch}` | 表示中。消えた後も、指が離れるまでは掛かりで続く |
| エディター（建物・マップ） | `{block = Everything}` | 動いている間。ゲームの一覧を使う間は `Everything & ~Touch` |
| 押し切りの設定 | `{defer = Start}`（利用者が選んだボタン） | 常時（メニューの設定の項目が置く） |

### 5.6 旧版の機能との対応

| 旧版 | 新しい API |
|---|---|
| ボタン遮断（1: スライドパッド以外の全部） | `block = group::Buttons`（SELECT は常に別枠） |
| 十字キーだけ遮断（2） | `block = group::DPad` |
| 全部（3: ボタン + スライドパッドのビット + アナログ値） | `block = group::Buttons \| part::SlidePad`。タッチは別に `part::Touch` |
| タッチ遮断 + 指が離れるまで（メニュー側の判定） | `block = part::Touch`。離れるまでは掛かりが続けるので、所有者は画面が消えた時点で要求をやめてよい |
| 押し切るまでボタンの遮断（A/B/X/Y/START） | `defer`。対象は `group::Buttons` の部分集合なら何でもよい（旧版は 5 つ） |
| 毎ティック `BlockGameXxx()` を呼び続ける間だけ有効 | 持続する要求（5.2）。理由は 9.3 |
| 優先順位 3 > 1 > 2 を 1 つの数値で表す | 区分の和集合。順序づけは要らない |
| 下画面ロック（暗幕とタッチ遮断を同時に切る） | 暗幕は描画側、遮断は要求。結び付けない（旧版も最後は別々に決めていた） |

### 5.7 エディターでの使い方（旧版の実績の引き継ぎ）

旧版のエディター（建物・マップ）は、動いている間、次のようにゲームの入力を止めていた。

| 旧版 | この設計 |
|---|---|
| 動いている間、毎ティック「全部」を頼む。プレイヤーが歩かない。ボタンとスライドパッドのビットとアナログ値を止める | `Set(owner, {block = Everything})` を開始で置き、終了で外す。ティックが止まると自然に解ける旧版の性質は、所有者の枠と開発版の一覧で見つける形に置き換える（9.3） |
| ゲームの一覧の部品を使う間だけ、タッチを止めない（一覧はゲームのタッチで動く） | 一覧が開いている間は `Everything & ~Touch` に置き換える |
| 自前の入力は CTRPF から読む。スライドパッドで盤面を動かし、十字・A・B は一覧へ渡す | CTRPF の入力は遮断と無関係なので、そのまま。ただし遮断中もゲームの一覧へ十字・A を渡す仕組みは別（下） |
| ゲームの一覧の部品の更新を自分で呼び、その間だけ部品が読む語（Wrapper の押した/リピート）へ実機のボタンと同じビットを一時的に書く | 遮断は calc の中で終わるので、calc の後に機能が一時的に書く方法は妨げない。この「供給」は遮断の部品に入れず、別に設計する |
| カメラを止める（ゲームの関数を書き換える） | 入力の遮断ではない。`world` の別の機構 |

エディターが止めた後、押されたままのスライドパッド・ボタンは、掛かりで離すまで届かない（旧版は、止めた瞬間に歩き出す・A で話しかける、が起きうる作りだった。コードの読み）。

### 5.8 試験の形

- `Table` は `core` の純粋な部品なので、`core` の試験と同じ形で、別スレッドの連続した受け渡しまで含めて確かめる（11.1 の A）。
- `Step` は時刻を引数に取り、ゲームにも CTRPF にも触れない。フレームごとの入力の列と要求の列を与え、「ゲームが見る保持・押した・離した」の列を出す。押した/離したは、ゲームの 0x00542E88 と同じ式（2.5）を試験側に書いた模型で作る。
- 4 節の手順を別の書き方で書いた参照モデルを試験に持ち、乱数の入力でも不変条件を確かめる（11.1 の B）。

## 6. 既定の方針（メニュー中に何を通すか）

| 区分 | メニューが閉じている | メニュー（ダイアログ・入力の枠を含む）が開いている |
|---|---|---|
| A・B・X・Y・L・R・ZL・ZR | 通す | **遮断** |
| 十字 | 通す | **遮断** |
| START | 通す（押し切りの指定があれば、離した時に 1 回） | **遮断** |
| SELECT | **常に遮断** | **遮断** |
| スライドパッド | 通す | **通す** |
| タッチ | 通す | **通す** |
| （全体） | SELECT が押されている間は、ボタン・十字・START も遮断（4.6） | 同じ |

押し切りの既定は START だけ（旧版と同じ。設定で A・B・X・Y・START などを選べる）。

### 6.1 旧版から変えた所と理由

利用者の判断事項は全て確定した。

| 判断 | 決定 |
|---|---|
| (a) SELECT が押されている間は他のボタン・十字・START も遮断（4.6） | 採用 |
| (b) 中断の掛かり（4.7）。CTRPF は通知、Rosalina は時間による推測 | 採用 |
| (c) メニュー中もタッチとスライドパッドを通す | 採用 |
| (d) 押し切りの既定は START だけ | 採用 |
| (e) 遮断の開始で離しを隠す。`kHideReleaseOnBlock` の既定は真 | 採用 |

| 変更 | 理由 |
|---|---|
| 開閉の境界で、押したままの入力の離し・押下を出さない | 利用者の条件。旧版は、保持の水準だけを消していたため離しが出る作りだった（2.5）。閉じた瞬間に押されたままのボタンも、旧版では新しい押下として届く作りだった（コードの読み）。 |
| SELECT が押されている間、ほかのボタンも遮断 | SELECT を使う組み合わせ（CTRPF の Select+十字上、Rosalina の L+下+SELECT、gohan のメニューの開閉）の相手がゲームへ漏れる。旧版は同時押しでの漏れを防いでいなかった。 |
| タッチは、メニュー自体は要求しない | 新しいメニューは上画面だけに出て、下画面のタッチは使わない。下画面の表示はゲームのままなので、触れなくする理由が無い。旧版は、メニューが下画面にあり、下画面の UI（キーボード・リスト）が出ている間だけタッチを遮断していた。同じ方針（下画面を使う側が要求する）で、要求する主体が変わっただけ。 |
| 区分をビットにして、重ねられるようにした | 旧版は 1 つの数値（0/1/2/3）とタッチの旗で、組み合わせられなかった。 |
| SELECT 遮断の場所を条件分岐の前に移した | 2.2 と 3.1。 |

### 6.2 変えなかった所

- スライドパッドを通す。止めるには方向のビットとアナログ値の両方を消す必要があり（2.8）、メニューを開いたまま歩ける既定は旧版の実機で動いていた。止めたい機能（エディター）は `part::SlidePad` を要求する。
- 開いている間はボタン・十字・START を遮断する。START も、メニューの設定に使うのでここでは遮断する。

### 6.3 メニューの要求の範囲

- メニューの要求は、エンジンが開いている間、およびダイアログ・入力の枠が出ている間（メニューが閉じていてもホットキーの確認のダイアログが出ることがある）。
- 遮断は、エンジンが論理的に閉じた時点（`Visible()` が偽で、ダイアログ・入力の枠も無い）で外す。退場の動き（320ms）の間はメニューが操作を受け付けず、ゲームが操作できる。押されたままのボタンは掛かりで続く。
- 遮断が掛かっているボタンは、押し切りの状態を捨てる（4.5）。メニューの中で START を押しても、閉じた後に遅れて届かない。

### 6.4 注意

- ホットキーで使うボタンのうち、押し切りに指定していないものは、押している間ゲームにも届く（旧版も同じ）。たとえば見本のホットキー L+Up では L と上がゲームに届く。ホットキーの先頭のボタンを自動で押し切りにする案は、普段の操作を遅らせるので採らない。
- 要求が効くのは次の周からなので、メニューを開く操作と同じ周に押された別のボタンは、その周だけゲームへ届く（SELECT の保護は同じ周のパッドの値で働くので、SELECT と同時に押したボタンは遮断できる）。

## 7. 導入・取り外し・失敗時

### 7.1 フックの仕様

| | フック P（パッド） | フック C（コントローラー） |
|---|---|---|
| 場所 | パッド読みの +0xF8（0x003534C8）、`LDR R0,[R4]` | calc の +0x24（0x0053CDE8）、`MOV R2,R9` |
| 元の命令の実行 | コールバックの前（標準） | コールバックの後（`EXECUTE_OI_AFTER_CB`） |
| コールバックが受け取る物 | R4 = パッド構造体 | R4 = コントローラー、R8 = 旧い保持、R9 = 旧い有効旗 |
| 返すときの契約 | **全レジスターを保存して返す**（R0 は元の命令の結果で、この後保存される） | R8・R9 を新しい値にして返す。ほかは保存して返す |
| 照合 | 関数の +0xF8 から 16 バイトの CRC-32 | 関数の +0x24 から 16 バイトの CRC-32 |
| 時刻 | 不要 | `svcGetSystemTick`（ミリ秒へ換算して `Step` へ渡す） |
| 実行 | パッド構造体の 3 語から SELECT を消す。生の SELECT を記録 | 規則 `Step` の適用 |

アセンブラの入口（`src/game/` に置く）は、毎フレームのフックの入口（`frame_callback.S`）と同じ形で、C の関数を 1 つ呼ぶだけにする。C 用の入口は、R8・R9 をスタックの 2 語に積んで C の関数へ渡し、返ったら読み戻す。

```
フック P:  push {r0-r12, lr}、フラグ・VFP を保存 → mov r0, r4 → bl gohan_input_pad → 復元 → bx lr
フック C:  R8・R9 以外を保存 → 2 語の領域に R8・R9 を置く → r0 = r4, r1 = 領域 → bl gohan_input_calc
           → 領域から R8・R9 を読み戻す → 復元 → bx lr
```

C の関数は次を守る。
- 待たない、確保しない、書式処理や記録をしない。表の読み取りは `Read` 1 回だけ。
- コントローラーの先頭の語が CtrController の仮想表（0x008FE6F8）でなければ何もしない（数えて状態に出す）。
- 書くのは `+0x10` のビット 0、`+0x110`、`+0x11C`、`+0x120`、R8・R9 だけ。

### 7.2 導入の手順

毎フレームのフックと同じ手順を、フックごとの機能（`Feature`）として行う。

1. タイトル ID を確かめる（違えば導入しない）。
2. ゲームを停止して（既に停止していれば解除しない）、対象の 16 バイトの CRC-32 を生成された値と照合する。読めない・不一致なら導入しない。
3. 元の命令の実行の指定（P: 標準、C: `EXECUTE_OI_AFTER_CB`）を設定して Hook を有効にする。
4. 結果（導入済み・タイトル違い・読めない・不一致・失敗）を状態として公開する。

機能は `game.input.pad`（P）と `game.input.controller`（C）の 2 つ。終了の段は「ゲームのフック」。`main.cpp` の登録は、毎フレームのフックの隣で行う。

### 7.3 失敗時の挙動

| 起きること | 結果 |
|---|---|
| タイトル違い・照合不一致・メモリを読めない | 該当のフックだけ導入しない。メニューは開く。状態に理由を出す。 |
| Hook の有効化に失敗（既に別のフックがある・容量） | 同じ。Wire は自分で元に戻して false。 |
| P だけ失敗 | ボタンの遮断は働く。SELECT は START としてゲームへ届く（メニューの開閉で START が反応しうる）。SELECT の保護と Rosalina の中断推測は働かない。CTRPF 再開の通知は C があれば働く。 |
| C だけ失敗 | SELECT は消えるが、メニューを開いてもボタン・十字・START・タッチはゲームへ届く。中断の掛かりは働かない。 |
| 両方失敗 | 従来どおり。要求は受け付け続ける。 |
| C の中でコントローラーが想定外（仮想表の不一致） | その呼び出しは素通し。数えて、状態に出す。 |
| 導入前に要求が置かれた | 受け付ける。導入されれば最初の周から効く。 |

導入に失敗しても、メニューを開かない（フェイルクローズ）ことはしない。メニューを開いたとき、C が入っていなければ、通知を 1 回出す（「ゲームへの入力の遮断を導入できていません。メニューの操作がゲームにも届きます」。理由は状態表示）。

### 7.4 取り外し

終了時、フックの機能は「ゲームのフック」の段で、ゲームを停止して Hook を無効にする（元の命令を CTRPF が復元する）。無効にした後でも、実行中だったスレッドがコールバックを抜けるのを妨げない（コールバックは 3gx の中にあり、プロセスの終了まで残る）。要求の表は残り、要求を置いても何も起きない。

取り外しの瞬間に押されていたボタンは、素の入力として届く（遮断が外れる。終了時のみの許容）。再導入は同じ手順で行える（開発版の入切の項目、10 節）。

### 7.5 状態の表示

通常版: 機能の状態を 1 行（導入済み / 未導入 / タイトル違い / 読めない / 照合不一致 / 失敗 / 終了済み、P と C を別に）。

開発版: 次を出す（CTRPF のメニューの「gohan」の項目の状態表示に、開発版だけ足す。文字の容量 `limits::StatusText` に収める。足りなければ容量を増やす）。

```
入力の遮断: パッド=導入済み 呼出 18203 / コントローラー=導入済み 呼出 18203 除外 0
  有効な要求: block=ボタン十字START+SELECT defer=START 世代 7
  所有者: reserved[SELECT] menu[ボタン十字START] settings[defer START]  競合 書き 0 読み 0
  いまの遮断: ボタン十字START 掛かり: A 保留: - 窓: - 通過: -
  累計: 離しを隠した 12 / 押下を隠した 9 / 掛かり 9 / SELECT 保護 4 / 中断の掛かり 1 / 押し切り 3 / 長押し 1
  フック P / C のスレッド: 同じ（確認済み）
```

- 各フックの導入結果と理由、呼び出し回数、除外回数（仮想表の不一致）。
- 有効な要求（`block`・`defer`・世代）と、所有者ごとの名前・要求。
- 表の競合（書き手の `Busy`、読み手の更新なし）の回数。
- いまの遮断・掛かり・保留・窓・通過。
- 累計: 離しを隠した回数、押下を隠した回数、掛かり、SELECT の保護、中断の掛かり、押し切りの渡した回数と長押しの回数。
- 2 つのフックが同じスレッドから呼ばれているか（スレッドの識別子を比べる）。
- 開発版の項目「開発: 入力の遮断 入・切」（導入と取り外しを繰り返して確かめる）。

状態はゲームのスレッドが 30 フレームごとに公開し（`Mailbox`）、表示はメニューのスレッドが読む。所有者の一覧は表の `List` で読む。

### 7.6 `spec/game_api.toml` への追加（案）

```toml
[[hooks]]
name = "InputPadRead"
function = "GameInput_ReadPadState"
offset = 248            # 0xF8（0x003534C8）
length = 16

[[hooks]]
name = "InputControllerCalc"
function = "sead_Controller_Calc"
offset = 36             # 0x24（0x0053CDE8）
length = 16
```

`globals` に CtrController の仮想表を足す。コントローラー・パッド構造体の型は、生成ヘッダーから使う。型の名前に解析の番号が入っているため、先にゲームの定義側で番号の無い名前に整えてから足す（gohan 側で別名を付けて回避しない）。`checks` は不要（この 2 つのフックの照合が同じ役目）。

## 8. CTRPF のメニュー・Rosalina との関係

| | CTRPF のメニュー（Select+十字上） | Rosalina（L+下+SELECT） |
|---|---|---|
| 入力の読み方 | CTRPF が OS の入力を直接読む | OS 側（Luma3DS）が自分で読む |
| ゲームの状態 | 開くとプロセスを止める。閉じると再開 | プロセスを止める |
| 遮断の影響 | 受けない。SELECT の遮断（P）も、要求（C）も、入力の読み方に関係しない | 受けない |
| フックが入っていなくても | 開ける | 開ける |

### 8.1 Select+十字上（CTRPF のメニュー）

- 現状: CTRPF の開く操作は SELECT。`ShouldOpenCtrpfMenu` が「十字上が押されている間だけ CTRPF を開く」と答え、`Shell::Step` は十字上が押されていない SELECT の押下で自前のメニューを開閉する。この規則は変えない。
- 遮断との関係: SELECT はゲームに届かない（P）。SELECT の保護により、SELECT を先に押したときの十字上もゲームに届かない。十字上を先に押す、または 1〜2 フレームの差で同時に押した場合は、十字上の押下がゲームへ 1〜2 フレームだけ届く（SELECT がまだ見えていない周）。十字上の離しは出ない（C が揃える）。
- CTRPF が開いてゲームが止まった後、再開時に押されたままのボタン（閉じる B など）は、中断の掛かり（4.7）で渡さない。
- 競合: CTRPF のスレッドの判定（十字上が押されているか）と、ゲームのスレッドの判定（自前のメニューを開閉するか）は、別のタイミングの入力で行われる。同じ SELECT の押下で両方が開く可能性は、実機で確かめる（12 節）。

### 8.2 L+下+SELECT（Rosalina）

- Rosalina は OS 側で動き、ゲームを止める。ゲームのパッド読みを変えても、Rosalina の入力は変わらない。
- 遮断との関係: SELECT はゲームに届かない。SELECT を最後に押す通常の順序では、L と下が数フレームゲームへ届く（OS が止めるまで。遮断が無い場合と同じ）。SELECT を先に押す順序では、SELECT の保護で届かない。
- 再開時: ゲームが止まっていた後の押されたままのボタンは、中断の掛かりで渡さない（SELECT を含む組み合わせの場合）。
- gohan のメニュー: Rosalina の組み合わせの間は、自前のメニューが SELECT の押下で開閉してはいけない。CTRPF と同様に、Luma3DS が設定している組み合わせ（`svcGetSystemInfo` の 0x10000 / 0x101）を `ui::input` が読み、押されているキーがその値と一致する間は、メニューが入力を受けない（組み合わせが終わり、全部離されるまで）。この読み取りと無視は遮断の部品ではなく、メニューの別の作業（次の課題）。遮断の部品は、この判定の有無に関係なく成り立つ。
- Rosalina の組み合わせを変えている場合（SELECT を含まない）: SELECT の保護と中断の掛かりは働かない。ほかのボタンの漏れと、再開直後の押下が起きうるが、害の小さい範囲。

### 8.3 遮断に求める性質（試験・実機で確かめる）

1. フックが入っていてもいなくても、CTRPF のメニューと Rosalina は開ける。
2. メニューを開く・閉じるときに、押したままのボタンの押下・離しがゲームに出ない。
3. CTRPF のメニューを閉じた直後に、閉じる操作のボタンがゲームの押下にならない（開く通知を使い、SELECT や 100ms の条件には依存しない）。
4. SELECT とそれ以外のボタンを同じ周に押しても、ゲームには START も他のボタンも届かない。

## 9. 旧版から引き継ぐ物・変える物

旧版は実機で動かしていた。実機の確認済みの物と、記録上は未確認の物、コードの読みから分かった弱点を分けて書く。gohan の実装には、旧版のコードをそのまま持ち込まない。

### 9.1 引き継ぐ物

| 旧版 | この設計 |
|---|---|
| 入力の遮断をゲームの入力（コントローラー）の層で行う | 同じ。calc の中で行う（3.1） |
| SELECT をパッド読みで、読み替えの前に消す | 同じ。ただし場所を条件分岐の前（0x003534C8）にした |

## 11. 試験

### 11.1 PC の試験

| 記号 | 対象 | 確かめること |
|---|---|---|
| A | `core/input_block` | 枠の借用・上限（Full）・不正（Invalid）。置き換えと解除。和集合（2 者が同じ区分を要求して片方がやめても残る）。同じ内容は Unchanged。SELECT が常に含まれ、0 番の枠は変えられない。競合時（別スレッドが公開中）に Busy で何も変わらない。複数のスレッドの連続した置き換えと読み取りで、公開値が壊れない（ある所有者の組み合わせからできる値だけが見える）。世代が変化したときだけ進む。 |
| B | `game/input_filter` | 下の不変条件と、場面ごとの列。 |
| C | `game/input_hook` | 導入の失敗の場合分け（タイトル違い・読めない・不一致・有効化の失敗）がフックごとに独立していること。P は標準の指定、C は後実行の指定で有効にすること。終了で 2 つとも無効になり、繰り返しても安全なこと。コントローラーの代役の記憶領域に対して、書き換えるのが決めた欄だけであること。仮想表が違えば何もしないこと。 |
| D | メニューの接続 | 開くと `Buttons` を要求し、閉じると外す。ダイアログ・入力の枠で要求が残る。Busy のときに次のフレームで置き直す。終了後は置かない。 |
| E | 設定 | 押し切りの設定が `defer` の要求になる。メニューの中で START を押した押し切りが、閉じた後に届かない。 |
| 変異 | B の試験の試験 | 規則の主要な条件を 1 つずつ壊した版（旧状態を揃えない、掛かりを外す、混ざりの判定を外す、遮断中の押し切りの状態を捨てない、タッチの保持のビットを落とさない、アナログ値を 0 にしない、SELECT の保護を外す、CTRPF の明示通知を無視する、100ms の境界を誤る、300ms の窓を終えない）で、B が必ず失敗すること。コンパイル失敗は検出成功に数えず、未変更の版の成功と、変異版の assert の失敗まで確認する。 |
| 検査 | `tools/check.py` | 層の向き（core は何にも依存しない、game は core だけ、menu は game・core）、番地の数値は game だけ、`atomic`・`volatile` は core だけ。 |

B の不変条件（乱数の入力でも確かめる。設計の検算として、4 節の手順を別に書いたモデルで、乱数 300 系列 × 400 フレームで 1〜5 に当たる条件を確かめた。実装では同じ形の試験を持つ）:

1. 遮断した区分は、保持・押した・離したのどれにも出ない。開始の瞬間の離しも出ない。
2. 遮断していない区分（掛かり・押し切りでもない）は、素通し。
3. SELECT が押されている間、ボタン・十字・START は出ない。
4. 遮断が終わっても、押されたままの区分は、離すまで出ない。離した後に押下・離しは出ない。
5. 押し切りの対象は、生の押下を出さない。窓・通過だけが出る。ほかのボタンが混ざれば窓は出ない。遮断中のボタンの押し切りの状態は捨てる。
6. 本体の押した/離したと Wrapper の押した/離したが、同じ値になる（同じ式を同じ R8・R9 から作る）。
7. タッチは、有効旗と保持のビット 15 の両方が落ちる。旧い有効旗も揃う。
8. スライドパッドの遮断で、方向のビットとアナログ値の 0 化が同時に起きる。
9. 中断: CTRPF 再開の明示的な知らせで SELECT や経過時間に関係なく掛かりになり、押し切りを捨てる。Rosalina 用の推測は SELECT の後に 100ms 以上空いた場合だけで、SELECT が無い長い周期や、その末尾で初めて SELECT を見た場合は掛からない。待ち受けは 30 呼び出しで終わる。

参照する列（参照モデルの出力と同じ形で、試験の表に持つ）: 押したまま開閉、遮断中に押し始めて終了後も押す、START の押し切りの単押し・START→十字上・十字上→START・押し直しの長押し・窓の重なり、SELECT→十字上と十字上→SELECT、タッチを置いたままの遮断、中断の後に B を押したまま。

状態の遷移を人が読めるよう、試験の列を表の形（フレーム・生の入力・遮断・ゲームの保持・押した・離した）で出せるようにする（`--trace` 相当）。

### 11.2 実機で確かめる手順

開発版（`make DEV=1`）の 3gx を使う。結果は「出た / 出ない」で記録し、「ゲームが反応する場面」は手順 2 で決めた場面を使う。

1. **導入**: 起動して状態表示を開く。P と C が導入済みで、呼び出し回数が増え続けること。CTRPF のエラーの表示が出ないこと（スレッドの領域の検査）。
2. **SELECT**: START を押すとゲームがはっきり反応する場面を 1 つ決める（例: 旧版で START に反応した場面）。その場面で SELECT を押す。自前のメニューは開くが、ゲームは START として反応しない。START を押すと、押し切りの指定が無ければ普段どおり反応する。
3. **メニュー中の操作**: メニューを開き、十字・A・B・X・Y・L・R を押す。プレイヤーの向き・道具・持ち物・会話などが変わらない。START も反応しない。
4. **開閉の境界**: B（走る）を押したままメニューを開く。走りが止まるだけで、離しの反応（滑る・道具をしまう）が出ない。B を押したままメニューを閉じる。閉じた瞬間に B の反応（走る・取り消し）が出ず、離して押し直すと反応する。A・十字でも同じ。
5. **通すもの**: メニューを開いたまま、スライドパッドでプレイヤーが歩く。下画面のタッチ（持ち物など）は反応する。
6. **失敗時**: 開発版の項目で遮断を切る（または照合値をずらした版）。メニューは開く。ゲームにも操作が届く。状態と通知が出る。入れ直すと元に戻る。
7. **押し切り**: START を押し切りに指定する。START 単押しで、離した時に 1 回反応する。START+十字上でゲームが START に反応しない。START を押し直して長押しできる。
8. **CTRPF のメニュー**: Select+十字上（十字上が先 / 同時 / SELECT が先）。自前のメニューが開かず、CTRPF が開く。ゲームは SELECT に反応しない。B で閉じて、B が押されたままでもゲームに反応が出ない。
9. **Rosalina**: L+下+SELECT。自前のメニューが開かない（別課題の完了後）。閉じて、押されたままのボタンがゲームに反応しない。
10. **取り外しと再導入**: 開発版の項目で入切を 100 回。落ちない。呼び出し回数が止まる / 再開する。終了してもゲームが落ちない。
11. **負荷**: 状態表示の呼び出し 1 回あたりの時間（`svcGetSystemTick`）がフレームの 1% 未満であること（開発版の数え上げに追加）。
12. **場面の一巡**: タイトル・村・家・持ち物・会話・下画面のメニュー・ミニゲーム・読み込みで、フックが働き続け、おかしな入力（勝手に押される・効かなくなる）が無いこと。

## 13. 選ばなかった案

| 案 | 選ばなかった理由 |
|---|---|
| OS の入力の共有メモリを毎フレーム消す（CTRPF の `InjectKey` と同じ領域） | 共有メモリは OS が非同期に書き換えるので、ゲームが読む前に消す保証が作れず、取りこぼすと漏れる。CTRPF 自身の読み取り（`hidScanInput`）も同じ領域なので、読む順序の管理も要る。 |
| ゲームの UI の部品が持つ「結び付いている」旗を消す | UI に登録された部品しか覆えず、移動・カメラ・当たり判定は別の経路。場面で配列が変わる。 |
| Wrapper（ゲームの各部品が読む側）で遮断 | Wrapper を介さず先頭のコントローラーを読む部品（共有のタッチ状態など）を逃す。 |
| パッド読みだけで全部遮断 | 押した/離したをコントローラーが旧状態から作り直すので、離しが出る。タッチは別の欄で読まれる。 |
| calc の `BL`（旧版の位置）で保持だけを消す | 離しが出る。Wrapper に渡す旧状態が揃わない。 |
| calc の `BL`（旧版の位置）で、R1・R2 と R8・R9 の両方を揃える | 可能だが、揃える物が倍になり、コールバックが R1・R2 を返す契約も要る。+0x24 なら R8・R9 だけで済む。 |
| SELECT を CTRPF の旗を見て弾く | CTRPF の処理は最後なので、開く 1 フレームだけ SELECT が通る。 |
| SELECT を START への読み替えの後で消す | 読み替えの後は SELECT と START を区別できない。 |
| 遮断の位置を `BLEQ`（旧版）にする | 条件が偽の経路で働かない。元の命令が条件付きなので、Hook の標準の指定では扱えない。 |
| 遮断の位置を PC 相対の `LDR`（0x003534D0）にする | 元の命令を Hook が実行できない。R0 にリテラルを入れ直すコールバックが要る。0x003534C8 は不要。 |
| コードを書き込む方式のまま | 3.2。 |
| 毎フレームに頼み直す要求（パルス） | 頼むのをやめれば自動で解ける利点はあるが、頼む周期と読む周期がずれると断続的に漏れる。所有者ごとの枠に持続して置く方が単純で、残留は開発版の所有者の一覧で見つける。 |
| 参照カウント式（Push / Pop） | 数が合わなくなると遮断が残る。所有者ごとの集合なら、各所有者の「いま」が分かる。 |
| 順序づけた数値のモード（0/1/2/3） | 組み合わせられない（タッチ・SELECT・押し切り）。 |
| 遮断の開始で離しを渡す | 利用者の条件に反する。水準で動く処理は止まるので不要。実機で問題が出れば、定数で切り替える（4.4）。 |
| 終了後の掛かりをやめる | 閉じる操作（B など）が新しい押下としてゲームに届く。 |
| 中断を時間の空きだけで検出して掛かりにする | 読み込み画面の長い周期でも掛かり、走る B などが効かなくなる。SELECT を起点にして範囲を絞る。 |
| スライドパッドを既定で遮断 | メニューを開いたまま歩ける既定が旧版の実機で動いていた。止めるには方向のビットとアナログ値の両方が要る。 |
| メニューが既定でタッチも遮断 | 新しいメニューは下画面のタッチを使わない。下画面を使う機能が要求する。 |
| 導入に失敗したらメニューを開かない | 利用者の条件に反する。メニューはどの場面でも開ける。 |
| 区分ごとの重ね合わせを領域（矩形）単位にする | 画面全体の入り切りで足りる。領域指定は旧版にも無い。必要になれば別に設計する。 |
| ホットキーの先頭のボタンを自動で押し切りにする | 普段のボタンの反応を遅らせる。利用者が選ぶ設定のままにする。 |
