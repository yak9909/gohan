# PC でメニューの見た目を確かめる

実機へ入れる前に、実際のメニューを決めた入力・時刻で動かして確認します。
`src/menu/`、`src/features/menu_screen/`、`src/ui/renderer/` を PC の C++20 コンパイラで
ビルドします。入力と時計、ゲームに描画指示を渡す境界には PC 試験の代役を使います。
メニューの処理・座標・文字の幅を別実装にはしていません。

## 実行

必要な物は Python 3.11 以上と PC 用の g++ または clang++ です。Python の追加パッケージと
ブラウザー用のライブラリは使いません。プロジェクト直下から実行してください。

```powershell
$env:PATH = 'C:\msys64\ucrt64\bin;' + $env:PATH
uv run --python 3.12 python tools/preview.py
```

`build/preview/index.html` をブラウザーで開きます。上400×240、下320×240 の PNG を
等倍と2倍で縦に並べ、各時刻を一覧にします。表示倍率は100%にしてください。
HTML は PNG・CSS を埋め込んだ1ファイルで、これだけを別の PC へ移しても見られます。
ROM を指定しない場合、生成物は `build/` 以下に置き、収録しません。

`--scenario entries` のように台本を絞れます。複数指定もできます。
`--dev` は開発版の項目を表示します。`--cxx` または `HOST_CXX` でコンパイラを選べます。
`--out build/preview-test` で別の出力先にできます。

`python tools/preview.py --parts --out build/preview-parts` で CA2 の自作 UI 部品の一覧を
出せます。全ボタンと全方向を含む画像を等倍・2 倍・分割で伸ばした形で並べ、
破線の繰り返し・位相・頂点色・切り抜きも描きます。実際の Canvas の描画指示と、
make と同じ生成器が作る RGBA8 の資源を使います。メニュー本体も同じ部品を使い、上画面に描きます。
資源の各チャンネルと設計表の色・不透明度は Python 試験で ±2 以内か検査します。
PNG は背景との合成後の色です。既定では実機の取得画像に合わせて RGB565 にも変換するため、
資源の色そのものを調べる時は `.rgba8` を復号し、PNG とは区別してください。
設計値は `spec/ui.toml`、自作の形は `tools/gohan_tools/codegen/ui_shapes.py` と
`ui.py`、字形の上書きは `glyph_overrides.py` を編集してください。

タイトル画面の背景も確認する場合は、作業ツリー外の展開済み RomFS（直下に `Layout/` がある場所）を
`gohan.local.toml` の `[rom] acnl_update_romfs`・`acnl_base_romfs` に指定します（任意、設定例は
`gohan.local.toml.example`）。更新を優先し、読み出しや形式の検査が失敗したら本体を試します。
未指定・両方とも失敗なら、窓の背景の重ね無し・一様な緑の帯です。

```powershell
python tools/preview.py --parts --out D:/gohan-preview/title-background
```

`--parts` の最後のページに、窓用のクリーム色の停止画像・帯用の緑の停止画像と元の 2 枚を出します。
実機と同じ C++ の復号・6 枚の合成を通します。窓は実機と同じ L4 を黒→白の色とペインの不透明度に相当する値で展開し、帯も L4 の黒→白の色で緑へ写します。GPU を使う実機側の排出待ちは PC の画像出力では再現せず、別の C++ 試験で検査します。設定は `--local <設定ファイル>` でも指定できます。
読み込み結果は出力先の `parts/background-status.txt` にあります。ROM の設定がある場合は入力・出力とも
作業ツリー内を拒否します。ゲームの資源・派生画像を gohan や SD に保存しないためです。
実行ファイルは常に `build/preview-runtime/` に置きます。帯は実機と同じ L4 合成で動き、撮影ごとに完成した画像も保存します。
`--no-rom` はローカル設定があっても代わりの絵を使います。PC 試験はこの指定で個人の ROM に依存させません。

## 台本とフレーム

既定の台本は `tools/preview/scenarios.json` です。開閉の途中、フォルダ、OFF／待機／ON、
適用前の黄色いON、予約／OK、数値の枠、選択の入力、通知、長押しの進み棒、閉じる前・
全適用・ホットキー実行の確認を含みます。各台本は別プロセスで初期状態から動きます。

別の台本は `--script tools/preview/example.json` で読み込めます。

```json
{
  "scenarios": [{
    "name": "example",
    "label": "開く動き",
    "events": [
      {"at": 32, "buttons": ["Select"]},
      {"at": 64, "buttons": []}
    ],
    "captures": [
      {"at": 0, "name": "closed"},
      {"at": 160, "name": "halfway"},
      {"at": 400, "name": "opened", "contains": ["GOHAN"]}
    ]
  }]
}
```

時刻 `at` は開始からの整数ミリ秒です。0から600000まで指定できます。
入力の時刻は昇順で重複させず、出力の時刻・名前も台本内で重複させません。
既定では16msごとに実際のフレーム処理を呼び、入力・出力の時刻がその間にあれば
その時刻にも呼びます。撮影時刻の入力を処理し、Canvas が確定した指示を保存します。
時刻は待ち時間ではなく仮想の時計なので、再実行しても同じ画像になります。

`buttons` は押しているボタン全体です。次に変更するまで保持されます。離すには `[]` を
指定してください。名前は `A B X Y L R ZL ZR Up Down Left Right Select Start` です。
`touch: [40, 60]`・`touch: null` はタッチを無視することの試験用です。メニューの操作には使えません。
`toggle: true` はそのフレームだけ外部の開閉要求を送ります。
`contains` はその時刻の描画指示に必要な文字があるか検査します。
`empty: true` は閉じた状態の描画指示が空かを検査します。

PNG は `<台本>/<出力名>-top.png` と `-bottom.png` です。`frame-N.json` に実際の描画指示、
`inputs.txt` に展開後の全フレーム、`fonts.json` と `atlas.la4` にビルドした字形資源を残します。
`manifest.json` には設定・台本・コンパイラの版・入力ソース等の SHA-256 を保存します。
字形は make と同じ生成器で `build/gen/font_atlas.hpp` を生成し、実際の `Fonts()` から取得します。
OS やブラウザーのフォントは描画には使いません。

## 上画面と色の設定

メニューは実製品と PC の両方で上画面（400×240）へ描きます。下画面の描画指示は空で、
タッチを与えても操作しません。`tools/preview/settings.toml` の `screen` は `top` のみを受け付けます。
PC 向けに製品のソースを置き換える処理はありません。

`--ca2-reference <見本のフォルダー>` で、CA2 の見本 17 場面と全台本の上画面を左右に並べます。
見本と出力先は作業ツリー外に置きます。`comparison/index.html` は各組の名前付き、
`all-scenarios.png` は全台本、`ca2-17.png` は見本 17 場面ごとの一覧です。
`metrics.json` に対応表と全画面の差を残します。台本と見本の状態・時刻が異なる組もあり、
差の数値を一致率としては扱いません。

比較時は通常の台本に加え、24 項目のスクロールの画面を PC 専用の定義で描きます。
製品の項目は増やさず、実際の Engine・Shell・Canvas を使います。
`--dev` なら開発用の行も表示し、見本の「値」の一覧と比べられます。
任意の `--background-top` で地の絵も合わせられます。

色・合成の較正値は同じ設定ファイルの `[raster]` にまとめています。

| 設定 | 既定値と意味 |
| --- | --- |
| `background` | `[32,40,48]`。ゲーム画面の代わりの不透明な地色 |
| `offset` | `[0,0]`。合成する全指示の整数座標の補正 |
| `alpha_gain` | `1.0`。頂点色の透明度に掛ける係数 |
| `rgb_gain` | `[1,1,1]`。各RGBの係数 |
| `swap_red_blue` | `false`。色順の診断用。通常は変えない |
| `rounding` | `nearest`。8 bitへの丸め。`floor` にもできる |
| `output_format` | `rgb565`。最終RGBを上位5/6/5 bitへ切り詰め、bitを反復して8bitへ戻す。診断用に`rgb888`も指定可 |

描画指示は `0xAARRGGBB` と解釈します。実機の頂点色への赤青の入れ替えはメモリ上の
並びを変える処理なので、プレビューの表示色は入れ替えません。
LA4 の8×8タイルをほどき、上位4bitの輝度と下位4bitの透明度を各17倍して使います。
RGBを輝度で、透明度をアトラスの透明度で乗算し、指示の順で
`出力 = 前景 × α + 背景 × (1−α)` を合成します。整数倍の字形は最近傍で描きます。
文字は実機側の Scene と同じく、縦は文字列全体、横は送り幅全体が切り抜き範囲へ
入る字だけを描きます。矩形の切り抜きは実際の Canvas が済ませた指示を使います。

今回確認した整数座標の文字・矩形以外の端の規則、テクスチャ補間、
合成途中の精度・丸め、色空間は未確定です。現在のアトラスは0/255だけなので、
中間のLA4値の実機確認も未実施です。
画面写真で測る前に、これらを確定済みの実機再現とは扱わないでください。
設定値は診断・較正のための補正で、ソースから分かる描画規則は書き換えません。

## 実機の画面写真との比較

Rosalina が保存した上・下画面の BMP を手元の入力として使います。
単独の400×240／320×240のほか、上が400幅・下が中央320幅の400×480画像にも対応します。
BMP は無圧縮24/32bit、PNG は不透明・8bit RGB/RGBA・非インターレースに対応します。
BMP の行の上下と BGR の順はヘッダーに従って処理します。ゲーム由来の画像を収録しません。

```powershell
uv run --python 3.12 python tools/compare_preview.py build/preview/states/opened-bottom.png build/captures/bottom.bmp --screen bottom --out build/comparison
uv run --python 3.12 python tools/compare_preview.py build/preview/states/opened-top.png build/captures/top.bmp --screen top --region 0 0 160 240 --luma --out build/comparison-top
```

同じ入力・同じアニメーション時刻・同じ背景で比べてください。透ける背景が違えば、メニューの
実装が同じでも差が出ます。メニューを閉じた状態の画面写真を
`--background-top build/captures/closed-top.bmp --background-bottom build/captures/closed-bottom.bmp`
でプレビューに与えれば、その背景に合成できます。動く背景や撮影時刻のずれは別途残ります。

既定のずらし探索は±4pxです。`--search 0` で位置を固定できます。
比較領域は `--region x0 y0 x1 y1`（右・下は含まない）で絞れます。
全候補に同じ画素数を使うため、画像の端から探索幅ぶんを除きます。実際の範囲を数値に残します。
`shift_capture: [dx,dy]` は「プレビューの `(x,y)` に実機の `(x+dx,y+dy)` を対応させる」の意味です。

出力は `difference.png`（差を4倍した白黒）、`comparison.png`（補正した実機・プレビュー・差分の順）、
`metrics.json` です。平均差・最大差・8／24を超える画素の割合・補正前の平均差を出します。
RGB モードは各画素のRGBの差の最大、`--luma` は `0.299R+0.587G+0.114B` の差を使います。
`signed_luma_mean_capture_minus_preview` が正なら実機が明るい傾向です。
位置→背景→色順→透明度→丸めの順で原因を分けて確認すると、誤った補正を重ねずに済みます。

## 2026-10-19 の実機較正

利用者の無圧縮BMP 4枚（400×480）で確認しました。上画面は `(0,0)` から400×240、
下画面は `(40,240)` から320×240です。比較入力・背景入力のどちらもこの並びを直接扱え、
切り出しや左右40pxの指定は不要です。同じ閉じたBMPを上下の背景に指定できます。

```powershell
uv run --python 3.12 python tools/preview.py --scenario states --scenario device-calibration --scenario device-capture-input --background-top ../device-shots/メニューを閉じた状態.bmp --background-bottom ../device-shots/メニューを閉じた状態.bmp
uv run --python 3.12 python tools/compare_preview.py build/preview/states/opened-bottom.png ../device-shots/メニューを開いた直後.bmp --region 4 4 158 216 --out build/comparison
```

写真のパスは手元の保存先へ置き換えてください。追加した `device-calibration/stamp-reserved`
は見本のスタンプを予約した状態です。`device-capture-input/flag-capture-input` は見本を開き、
Lを2100msから押し、2120msに下も押した直後です。撮影操作で全戻しの長押しが始まり、
選択枠がフラグ側に残ったまま押下中へ移り始める状態を再現します。

確認は次の順で行いました。

1. **位置**: メニュー帯の領域 `[4,4,158,216)`、32,648画素で±4pxを探索。
   開いた状態・予約状態・撮影入力の状態はいずれも `(0,0)` が最小。座標の補正は `[0,0]` を維持しました。
   文字の細線、幅2pxの右端、1pxの説明枠に一律のずれはなく、端の画素に追加のずらしは入れません。
2. **背景**: `Panel::Draw` は左160pxの帯だけを、`DrawDescription` は右の説明窓だけを塗ります。
   右の窓の外には描画指示がありません。閉じた写真を背景に合成すればその領域が残るので、
   メニュー側の塗りや不透明度は変更していません。差分画像では右の動く模様と文字に残差が集中します。
   閉じた状態のプレビューは写真と全76,800画素が一致。開いた状態の全画面平均差は、
   単色背景94.327から写真背景9.604へ減りました。
3. **色順**: 赤青は交換しません。固定色の文字 `(174,185,177)` は実機の `(173,186,181)` に対応し、
   下記のRGB565化と整合します。`rgb_gain=[1,1,1]` を維持しました。
   赤青を交換すると全画面平均差は9.604から10.996へ増えました。
4. **透明度**: `alpha_gain=1.0` を維持しました。写真間で背景の模様の位相が変わり、
   選択枠も脈動するため、その差を全体の透明度へ吸収する根拠はありません。
   係数0.95／1.05の診断値は平均差13.093／12.475で、1.0の9.604より悪化しました。
5. **丸め・色段階**: 4枚とも下画面76,800画素の全てがRGB565の展開値に一致しました。
   `rounding="nearest"` の8bit合成後、最終出力をRGB565へ量子化します。
   R/Bは `n=v>>3; (n<<3)|(n>>2)`、Gは `n=v>>2; (n<<2)|(n>>4)` です。
   途中の合成ごとの量子化は最終段だけより差が増えました。これは出力の経験的な補正であり、
   GPU内部の全ての合成精度を確定するものではありません。

同じ閉じた背景で、メニュー帯全体 `[0,0,158,240)` のRGB最大成分差の平均を測りました。

| 状態 | 8bit・nearest（従来） | 最終RGB565・nearest（採用） | 最終RGB565・floor | 合成ごとRGB565・nearest |
| --- | ---: | ---: | ---: | ---: |
| 開いた状態 | 5.869 | 4.500 | 4.634 | 4.633 |
| スタンプ予約 | 7.805 | 6.711 | 6.847 | 7.052 |

採用設定の位置探索領域では、開いた状態の平均差4.906、差>24は1.231%、
予約状態の平均差7.187、差>24は3.400%でした。全画面の平均差はそれぞれ9.604／17.450で、
帯外の動く背景の影響が大きいため、全画面の数値だけでは係数を決めていません。
撮影入力の状態は同じ探索領域で平均差2.241、差>24は0.631%、全画面平均差4.866でした。
差分の文字の輪郭は重なり、明るく残るのは主に背景の模様・選択枠・説明枠の下の透けです。

証拠は作業場の `_local/evidence/gohan-18/` に保存しています。
`calibration-metrics.json` に位置探索・全画面・色順／透明度の診断値と写真のSHA-256、
`rounding-sweep.json` に丸め候補の数値、`*-comparison.png` に実機・プレビュー・4倍差分、
`*-difference.png` に差分を残しました。写真・比較画像・測定用スクリプトは収録しません。
`*-full-comparison.png`／`*-full-difference.png` は領域を絞らない全画面版です。
動きの時刻が厳密に一致する写真、上画面でのメニュー、非整数座標、中間LA4値は未確認です。

## CA2 の動く帯と実機の直しの検証範囲

帯の150コマを導入前に同じC++の合成で作り、1024×256と1024×64のL4の2ページへ詰めます。
実行中は毎フレームGPUの参照範囲を選びます。CPUの合成・転送・二重画像の再利用待ちはありません。
GPU用の背景画像は合計198,656バイト、字形・UIも含めた画像全体は297,472バイトです。既存の低空き容量時の代替色と排出待ちは引き続き使います。
プレビューも同じアトラスと参照範囲を使います。

`device-motion` は操作の帯の固定位置のフェード、スイッチの往復、選択文字の中間色、窓の退場を撮影します。
`device-seven` は7件の通知とメニューの重なり、追加・終了に伴う積む位置の移動を撮影します。
7件の長文は本文を1行へ省略し、操作の帯を残して画面内へ収めます。
ホスト試験では24項目・スイッチ10行・長い説明・7件と退場中の1通知・選択とスクロール途中を実際のCanvasへ通し、
板・文字枠・記録量と捨てた指示を検査します。

実機のフレーム時間、導入前の全コマ合成の時間、背景との動きの一致、
不透明度0.85で動くゲーム画面を透かした時の読みやすさは再確認が必要です。

`folder-motion` はフォルダへ入る・戻る時の一覧の横移動とフェード、パンくずのクロスフェード、途中で戻って再び入る入力を連続コマで撮ります。
開始16 msも含めて、行が表示範囲の x=23〜210（右端は含まない）で切られ、指が最前面に残ることを確認できます。
選択の帯は旧・新の行それぞれに含め、同じ横移動・フェードと縦の選択移動を重ねます。
`overflow-motion` は8件目で押し出される通知と、残る通知の積む位置の移動、360 ms後に始まる新しい通知の入りを40〜80 ms間隔で撮ります。
積み替え中に下の2件が重ならず、空いた位置へ新しい通知が入ることを確認できます。
両方とも `tools/preview.py --scenario <名前> --no-rom` で単独実行できます。

PC のメニュー画面試験は、行と帯に同じ表示範囲が付くこと、指の描画順、帯とスイッチの相対位置を検査します。
通知は積み替えから入りの完了まで1 ms刻みで新規の矩形と全ての既存通知の矩形を比較します。
初回描画が80 ms遅れた場合も含め、見え始める前に積み替えが終わることと、矩形の重なりが無いことを確かめます。

通知の地は専用の `ca2.color.notice.paper`（0.95）で描き、ほかの窓（0.85）と分けます。
